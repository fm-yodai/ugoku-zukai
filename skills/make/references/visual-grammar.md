# 演出の約束（VG-）

台本の動作（`do`）で画面をどう動かすかの約束。writer は台本を書くときに、director はスライドの動作と行ごとのコマを判定するときに読む。基準（`criteria/`）は番号で参照する。動詞の引数と既定の長さは `storyboard.md` の 5 章が正。

ここに書くのは、今の動詞で言える約束だけ。VG-10〜VG-12（Morph・カメラ・線の描画）は `ugoku-zukai/4` の表現で、効く場面が限られる。どの約束も回数の決まりではなく、なぜ効くかを読んで、スライドの意図に合うときに使う。

## 目次

- VG-1 データが主役
- VG-2 色の役割は図をまたいで同じ
- VG-3 1 行に 1 つの画面変化
- VG-4 寄って、戻る
- VG-5 具体的な 1 件を通す
- VG-6 強調は字幕の主題に付ける
- VG-7 応答は別の矢印で、来た道を戻る
- VG-8 残り物は消す
- VG-9 出す順は、説明の順に合わせる
- VG-10 同じものが育つなら、Morph でつなぐ
- VG-11 カメラは、話している 1〜数個に寄せる
- VG-12 線を描くのは、線の形を追わせるときだけ

## VG-1 データが主役

- 約束: 処理の流れを追う詳解の場面では、流れているデータ（リクエスト・トークン・レコード・申請書）を画面に出すと、何が渡っているかが伝わる。箱と矢印は、そのデータが通る場所を示す背景になる。箱の関係を見せたいだけの図では要らない
- 使う動詞: `trace`（`label` にデータの名前）、`relabel`（データの値が変わるところ）、`note`（調べられる中身）
- 悪い例: 詳解の場面が `show` と `pulse` だけで、箱が順に光るだけ。何が渡っているのかが画面に一度も出ない

## VG-2 色の役割は図をまたいで同じ

- 約束: 色は役割（`role`）で決め、同じ意味には動画を通して同じ役割を使う。`added`・`good` は増えた・うまくいった、`removed`・`bad` は消えた・失敗、`warn` は注意
- 使う動詞: 図の宣言の `role`、`tint`（`as` に役割）、`reply`（`as` に役割）、`mark`（`as` に `check`・`cross`・`question`）
- 悪い例: 正常な応答の戻り矢印を `bad` で引き、失敗したように見える。前の図で「人」だった色を、次の図で保存先に使う

## VG-3 1 行に 1 つの画面変化

- 約束: 1 行の字幕で起きる画面の変化は 1 つが目安。字幕の文中の印（`at`）でその語を話す瞬間に結ぶ。続けて起きる小さな動作（点が着いたら光る）は 1 つの変化に数えてよく、同時に出すほうが分かるもの（対になる 2 つ）はまとめて出してよい
- 使う動詞: すべての動詞。`at` と `after` で時刻を結ぶ
- 悪い例: 1 行の中で、点がたどりながら別の箱に注記が出て、右上の札も変わる。どこを見ればよいか分からず、動作が声より長くなる（`frames.json` の `sub_forced`）

## VG-4 寄って、戻る

- 約束: 全体図の一区間を説明するときは、その区間だけを残して周りを薄くすると、どこの話かが分かる。説明が終わったら全体に戻すと、次の区間との関係が見える（そのまま次の区間に寄るほうが自然な流れなら、戻さなくてよい）。周りは消さずに薄くする（位置の関係が残る）
- 使う動詞: `focus` → 説明 → `unfocus`
- 悪い例: `focus` したまま次の区間に移り、全体図のどこを見ているのかが分からなくなる。周りを `hide` で消して、隣の部品との関係が見えなくなる

## VG-5 具体的な 1 件を通す

- 約束: 「データが流れる」と抽象で言うより、1 回のリクエスト・1 件の申請を端から端までたどると伝わりやすい場合がある。概念の説明なら、1 つの事例を表の行や全体図の上で進める。短い紹介や概観では、1 件を通すと長くなるので要らない
- 使う動詞: `trace`（同じ点の `dot` を使い続ける）、`relabel`（その 1 件の値が変わる）、表なら `show` で行を足して `mark`
- 悪い例: 場面ごとに別の点を出し、前の場面の 1 件がどうなったかが追えない

## VG-6 強調は字幕の主題に付ける

- 約束: 強調は、その行の字幕が話している要素にだけ付ける。字幕が次の要素に移ったら強調も移す
- 使う動詞: `pulse`、`mark` / `unmark`、`focus`、`tint`
- 悪い例: 字幕が 3 つ目・4 つ目の項目を話しているのに、`mark` が 1・2 項目目に残っている
- 比べる図（ベン図・比較・2×2 など）では、説明の主役の側に強調の色（`role: "accent"` など）を置き、比べる相手は控えめな役割にする。主役は、構成メモの章やスライドの意図から読む

## VG-7 応答は別の矢印で、来た道を戻る

- 約束: 線は一方向にする。応答は別の矢印で描き、実際の呼び出しの経路を逆にたどって戻す（途中の部品を飛ばしてクライアントへ直接戻さない）
- 使う動詞: `reply`（区間ごとに逆向きの辺を宣言する）、`sequence` ならメッセージの `reply: true`
- 悪い例: 1 本の辺で行きと戻りの両方を表す。ミドルウェアの拒否を、間のアプリを飛ばしてブラウザへ直接引く

## VG-8 残り物は消す

- 約束: 前の行で出した一時的なもの（点・注記・印・札）は、役目が終わったら消す。残すなら、次の行の字幕と同じ意味で読めるときだけ
- 使う動詞: `hide`（点は `dot:<名前>`、注記は `note:<id>`）、`unmark`、`badge` に `""`
- 悪い例: 前の場面の点が箱に残り、次の場面でも何かが流れているように見える

## VG-9 出す順は、説明の順に合わせる

- 約束: 部品や要素は、字幕がそれを話す順に出すと、聞きながら目で追える。図の作りの順（外から内、上から下）が、話す順と同じとは限らない
- 使う動詞: `show`（要素ごとに `at` で結ぶ）
- 例（利用者が直したもの）
  - 包含のベン図で「ユーザビリティは UX の一部」と話すなら、内側（ユーザビリティ）を先に、外側（UX）を後に出す
  - 循環図の中心（「繰り返す」）は、各段階を言い終えてから出す（SP-17 の、画面での対応）
  - 2 軸の図で象限を説明するときは、象限ごとに具体例を 1 つ添えると、軸の意味が伝わりやすい場合がある
- 悪い例: 外側の円から出し、字幕はまだ内側の話をしている。循環図の中心が最初から出ていて、まだ紹介していない「繰り返す」が先に見える

## VG-10 同じものが育つなら、Morph でつなぐ

- 約束: 構成が段階的に育つ（部品が 1 つずつ増える）、同じ表や一覧の before / after を比べる、のように「同じものが続いている」ことを聴衆に分かってほしいときは、段階ごとに 1 枚のスライドにして、後のスライドの部品に `morph` を書く。共通の要素は動かずに残り、増えた所だけが現れるので、どこが変わったかを目で探さずに済む。別々の 2 枚に見えると、聴衆は前の図と見比べて違いを探すことになる
- いつ決めるか: Morph は「v1 の 1 枚 → v2 の 1 枚」というスライドの並びが前提なので、スライドを切る段階で決める。原稿や動作を書く段階では手遅れになる
- 書き方の要点: つなぎたい要素には、どの段階でも同じ id を書く（`graph` のノード、`list`・`table` の項目と行、`compare` の項目）。自動で振られる連番の id はつながらない。`graph` は系列の全段階を 1 枚のキャンバスに置くので、前の段階の箱は動かず、v1 のスライドは v1 の部分に寄って大きく写る。後から増える部品も、最初から同じ構成の中の場所として考えておく
- 使う動詞: 部品の `morph`（直前のスライドの、同じ `type` の図の id）。増えた要素は、スライドの `start` に従って出る（省いたら `show` で出す）
- 乱用すると: 中身が違う 2 つの図をつなぐと、別のものが同じものに見える。どのスライドの切り替えも動くと、動きが「育った」の合図にならなくなる
- 良い例（`examples/camera-morph.json`。キャッシュを足した 1 枚が、前の 1 枚から育つ）

```json
"arch-v2": { "title": "キャッシュを足した構成",
  "statement": "よく読まれるページは、キャッシュが DB の手前で返します。",
  "parts": [ { "figure": "v2", "morph": "v1", "area": { "col": [1, 12], "row": [1, 4] } }, … ] }
```

- 悪い例: 構成が 3 段階に育つ章を、3 枚の独立した `graph` で描き、段階ごとに箱の並びが入れ替わる。同じ箱の id を段階ごとに変えて（`app` → `app2`）、つながらない。構成図の次の 1 枚が、同じ箱を使った別の話（処理の流れ）なのに `morph` でつなぎ、構成が変わったように見える

## VG-11 カメラは、話している 1〜数個に寄せる

- 約束: 全体図の中の 1 か所（数個の要素）だけを話す行で、その場所が小さくて読みにくいときは、`zoom` で寄せる。寄せるのは本文の領域だけで、見出しと言いたいことは残るので、何の話かは消えない。話が全体に戻るときは `{"zoom": "all"}` で戻すと、寄った場所が全体のどこだったかが分かる。隣の要素へ話が移るだけなら、`pan` で倍率を保ったまま移る
- なぜ効くか: Prezi の資料を調べた研究では、うまく流れる資料のズームは、そのとき話している 1〜数個の要素に注意を集めるものだった。一方で、ズームを入れれば分かりやすくなるという結果は出ていない（Prezi 自身もズームのしすぎに注意を促している）。全体図から寄って戻る動きは、周りとの位置関係を保ったまま注意を集めるときにだけ効く。`focus` で周りを薄くするだけで読めるなら、寄せなくてよい（VG-4）
- 使う動詞: `{"zoom": "<id>" | ["id1", "id2"], "pad": 40, "at": "b"}`（配列なら、それらを囲む範囲に寄る）、`{"zoom": "all"}`、`{"pan": "<id>"}`。寄せる先は、もう出ている要素にする。スライドが変わると、カメラは全体に戻る
- 乱用すると: 1 行の中で何度も動く、行ごとに寄ったり戻ったりすると、せわしなく、見ていて疲れる。全体が十分読める図で寄ると、装飾の動きになり、全体の関係が見えなくなる
- 良い例（`examples/camera-morph.json` の l13〜l14。込み入った右側の 3 つに寄せ、言い終えたら戻る）

```json
{ "id": "l13", "text": "{a}DB への変更は、{b}レプリカに複製されます。",
  "do": [ { "at": "a", "zoom": ["cache", "db", "replica"], "pad": 20 }, { "at": "b", "show": "db>replica" } ] },
{ "id": "l14", "text": "{a}全体に戻ると、読み取りはキャッシュとレプリカが受け持ち、DB は書き込みに専念できます。",
  "do": [ { "at": "a", "zoom": "all" } ] }
```

- 悪い例: 箱が 3 つしかない図で、1 行ごとに箱へ寄っては戻る。寄ったまま次のスライドの話を始め、全体のどこにいるのかが分からなくなる（VG-4 と同じ）

## VG-12 線を描くのは、線の形を追わせるときだけ

- 約束: 経路そのもの（どこからどこへ渡るか、どこを回り込むか）や、囲みの範囲を目で追ってほしい線は、`show` に `"draw": true` を書いて、始点から伸ばして出す。聴衆の目は伸びる線の先を追うので、字幕が経路を話す間、目が経路に沿って動く
- 使う動詞: `{"show": "app>replica", "draw": true}`。線を持つもの（箱の枠、実線・破線の辺、`frame`）に効く。線のないもの（テキストなど）に書くと、普通の `show` になり、検査が警告する
- 乱用すると: どの `show` も線から描くと、出るまでに時間がかかり、動きが情報を持たなくなる。部品を出すだけの行は、普通の `show` で足りる
- 良い例（`examples/camera-morph.json` の l12。読み取りの行き先が DB から分かれる線を、話しながら伸ばす）

```json
{ "id": "l12", "text": "{a}アプリは、読み取りをレプリカへ送り、書き込みだけを DB へ送ります。",
  "do": [ { "at": "a", "show": "app>replica", "draw": true } ] }
```

- 悪い例: スライドの部品すべてを `draw` で出し、経路の話でない行まで線が伸びる。テキストの部品に `draw` を書く
