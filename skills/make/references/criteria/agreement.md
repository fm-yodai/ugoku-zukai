# 意図との照合の基準（A-）

台本（`storyboard.json`）のスライドと原稿が、利用者と合意した構成メモ（`outline.json`）の意図どおりかを見る。台本の場面は `chapter` で構成メモの章を指し、構成メモのスライドと台本のスライドは同じ id で結ばれている（`../storyboard.md` の 3 章と 8 章、`../outline.md`）。最初のスライドコンテを見せる前と、スライドを直した後に判定する（`target` は `script`）。

照らす意図は 3 段ある。章の順番の意図（`flow`）、章の意図（`intent`）と前の章からのつながり（`link`）、スライドの意図とつながり（章の `slides` の `intent`・`link`）。利用者が必ず入れたいと言った内容は、章かスライドの意図の文に書き込まれている。

ここで見るのは、スライドが意図どおりかである。原稿が、スライドとその意図どおりかは、スライドが固まった後に `script.md` の S-W12・S-W13 で見る。

「元」の列は、作り直す前の基準の ID。

指摘の場所（`where`）は、スライドへの指摘なら、そのスライドを最初に使う場面の id（`s3`）にし、`problem` の頭にスライドの id を書く（「スライド `ux-def`: …」）。章の意図への指摘は章の id（`c3`）、原稿の行への指摘は行の id にする（`../writing/review-format.md`）。

**どの判定にも、意図のどの文に照らしたかを書く。** `evidence` に、意図の場所と文の引用、照らしたスライドの文言（見出し・言いたいこと・部品の文字）を並べる（「`ux-def` の `intent`『UX の定義の文そのものを読み、範囲が…に及ぶと分かる』に対し、スライドには定義の囲みがなく、図だけがある」）。

A- の指摘は、直すと合意した内容が変わることが多い。直し方が 2 つあるとき（スライドを意図に合わせる / 意図をスライドに合わせる）は、`suggestion` に両方を書く。どちらにするかは利用者が決める。スライドの切り方（1 枚を分ける、2 枚をまとめる）を変える案は、進行役が案を並べて利用者に選んでもらう材料になる。

## 較正の例

- **1 語の付け足しが must になった**（通しでの例）: 「生成AIで作るプロトタイプ」と、意図にない 1 語を足していた。意図に生成AIの話はないが、章の言いたいことは変わらない。評価役は should と付けたのに、A-2 が must だけの基準だったため、利用者に全文で見せる指摘になった。この程度の付け足しは should → A-2

- **定義の文が画面になかった**（スライドを先に作る進め方に変えるきっかけになった通し）: UX の定義を説明する場面で、定義の文そのものを画面に出したかったが、画面には図しかなく、定義は字幕で言うだけになった。今の形で、スライドの意図が「定義の文そのものを読む」なのに、完成形に定義の文がなければ → A-3
