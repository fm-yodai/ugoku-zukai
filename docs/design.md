# ugoku-zukai（動く図解）設計

前身は個人用のスキル explain-video-anywhere（v1。Manim＋VOICEVOX の Docker）。

- 作成: 2026-11-05
- 状態: 下書き（画風・描き方・名前・公開先まで合意済み。未決事項は末尾）
- リポジトリ: github.com/fm-yodai/ugoku-zukai（非公開で作り、ライセンス表示が整ったら公開する）

## 1. 目的

題材を、ナレーション付きの解説動画にする。題材はコード・リポジトリ・PR・Web ページ・文書・題目だけ、のどれでもよい。claude.ai / Claude Desktop のチャットでも Claude Code でも同じ品質で作れるようにし、プラグインとして配る。

## 2. 要件（ユーザーと合意済み）

| 項目 | 内容 |
|---|---|
| 成果物の形 | 再生できれば形式は問わない。HTML の再生ページを基本にし、mp4 は必要なときに書き出す |
| 声 | 自然な日本語のナレーションが必須 |
| 動かす環境 | claude.ai / Desktop のチャットと Claude Code を最優先にする |
| 視聴者 | 主に社内の非開発者 |
| 題材の範囲 | すべての種類を扱う（文書や題目も NotebookLM に任せない） |
| 画風 | 柔軟に選べるようにする。インタビューで聞く。デザインシステムを受け取り、それに沿って描けるとよい |
| 描き方 | 標準は「決まった語彙の台本＋自動配置」。場面ごとに自由なコードで描く方式（manim-web）も選択肢として持つ |

## 3. 検証で確かめた事実（2026-11-05、claude.ai Team）

検証用スキル `tools/probe/evx-probe` を claude.ai で実行した結果。

- **サンドボックスの通信**: 許可したドメインにだけ届く方式。届くのは GitHub（release-assets を含む）、PyPI、npm、api.anthropic.com など。Google の API、ElevenLabs、Hugging Face、jsDelivr には届かない
- **サンドボックスの道具**: ffmpeg・node・npm・uv・日本語フォント（IPA、Noto Sans CJK）がある。chromium・docker・sudo はない。CPU 1 つ、メモリ 4GB
- **VOICEVOX**: voicevox_core 0.17.1 が `pip install --break-system-packages` で動いた。ダウンロードは計 23.5 秒（約 94MB）。合成は 222 文字（音声 41.9 秒）に 32.6 秒かかり、5 分の動画なら約 4 分になる
- **再生**:
  - WebAudio での再生は、すべての経路で成功した
  - チャット上のプレビューでは、audio 要素も Blob URL も「URL safety check」で拒否された
  - Artifact では audio 要素も鳴った
- **公開**: サンドボックスで作ったファイルを、書き写さずにそのまま Artifact として公開できた
- **ダウンロード**: Artifact の中から始めたダウンロードは止められた（downloads capability の宣言が要る）。チャット上のプレビューでは保存できた
- **mp4**: 視聴者のブラウザで H.264・AAC・Opus をエンコードでき、MediaRecorder も使える
- **Motion のひな形**: claude.ai の Motion はナレーションを入れられない（音は BGM と効果音だけで、長さは 300 秒まで）ので使わない

## 4. 全体の流れ

> この章の流れ（インタビュー → 取材と契約 → …）は、15 章の作り直しで置き換えた。下は当初の設計の記録として残す。

```
0 インタビュー ─ 読者・一番分かってほしいこと・範囲・構成の型・長さ・声・画風（とデザインシステム）・描き方
1 取材と契約   ─ brief.md と contract.json（根拠つき）        … v1 を引き継ぐ
2 台本         ─ storyboard.json（字幕・読み・根拠・ops）       … v1 を引き継ぎ、ops を新しいプレーヤーに合わせる
3 音声         ─ voicevox_core で 1 行ずつ合成し、mp3 にまとめる
4 組み立て     ─ 台本・画風・音声を HTML のプレーヤー 1 枚に埋め込み、配置を検査する
5 公開         ─ Artifact で公開する（mp4 はプレーヤーから書き出す）
```

### 環境ごとの違い

| | Claude Code | claude.ai / Desktop のチャット |
|---|---|---|
| 作り手と評価役 | サブエージェントで分ける（`ugoku-zukai:researcher` など。v1 の evx-* を移したもの。評価役は作り手と別のモデルにする） | サブエージェントがないので、1 つの会話で役を順番に演じる。評価役の番では、作り手の推論を読み返さずに基準ファイルだけで判定するよう指示する |
| 機械検査 | 同じスクリプトを使う | 同じ |
| VOICEVOX の導入 | `${CLAUDE_PLUGIN_DATA}` に 1 回だけ入れる | 会話のたびに入れる（約 25 秒） |
| 配置の検査 | node で行う（下の 6.3） | 同じ（サンドボックスにも node がある） |
| 公開 | Artifact | Artifact |
| インタビュー | AskUserQuestion | ask_user_input などのフォームがあれば使い、なければ文章で聞く |

## 5. 描画

### 5.1 3 つの描き方

| 描き方 | 中身 | 向いている題材 | 長所 | 短所 |
|---|---|---|---|---|
| **標準: 宣言型＋SVG プレーヤー** | Claude は ops（`map_show` / `travel` / `respond` など）だけを書き、決まったプレーヤーが描く。配置は ELK が決める | 処理の流れ・構成・変更前後・業務フロー（大半の題材） | 配置崩れが起きにくい。機械で検査できる。毎回同じ品質。軽い | 語彙にない見せ方はできない |
| **抜け道: 行ごとの自由描画** | 標準のプレーヤーの中で、`{"op": "custom"}` の行だけ、時刻 t を受け取って描く JS 関数を Claude が書く（補助の関数群を用意する） | 語彙で表せない演出が 1〜2 場面だけ要るとき | 標準の安定を保ったまま幅を足せる。よく使う形は語彙に格上げできる | その場面だけ検査が甘くなる |
| **manim-web モード** | 動画全体を manim-web（ブラウザ版 Manim）で、場面ごとのコードとして書く。時刻 t から画面を決める層は自前で持つ | 数式・図形の変形・3D、アイコンや斜めの線など手作りの絵が要る題材 | 表現の幅が一番広い。3b1b の質感に近い | 座標を手で置くので配置崩れが起きやすい。0.x 版で、ドキュメントにない不具合がある（0.41.0 で 3 つ確認）。本体の約 3.2MB を CDN から読む（claude.ai の Artifact で読めるかは未確認）。日本語の文字を書き順で描く演出は使えない |

- 描き方はインタビューで決める。既定は標準で、題材が数式・3D のときだけ manim-web を勧める
- manim-web のバージョンは固定する。見つけた不具合と回避方法は `references/manim-web.md` に書いて育てる

### 5.2 プレーヤー（標準と抜け道）

試作は `prototypes/compare/svg/player_template.html` にある。

- **HTML 1 枚**: 台本 JSON・画風・音声（mp3 の base64）を埋め込む。外部から読むのは elkjs と（手描き調なら）rough.js だけで、どちらも版を固定する。claude.ai で CDN から読めない場合に備え、同梱して直接埋め込む形も用意する（elkjs は約 1.5MB）
- **画面は時刻 t だけで決まる**: 毎フレーム「既定の状態 → 台本の動作を時刻順に重ねる → DOM に反映」で描く。どこへでも飛べ、mp4 にも同じコマが書き出せる
- **音声は WebAudio の時計に合わせる**: audio 要素は使わない（チャットのプレビューで拒否されるため）
- **字幕とクレジットは画面に描く**: mp4 にしても残る
- **v1 から移す語彙**: v1 の ops の数は 40 前後。最初に移すのは、全体図・点の移動・応答・強調・薄くする・札（試作で実装済み）と、表・トークン・コードの重ね表示・題・箇条・クレジット。次に、シーケンス図・状態遷移図、`what_if` / `scan` / `halt` などの演出を移す

### 5.3 mp4 の書き出し

- プレーヤーに「mp4 で保存」のボタンを付ける
  1. SVG のコマを順に canvas に描く
  2. WebCodecs でエンコードする
  3. mp4 にまとめる（Mediabunny などを使う。選定は未決）
- Artifact では downloads capability を宣言して保存させる
- Claude Code では、Playwright でプレーヤーを動かして書き出す方法も用意する

## 6. 画風とデザインシステム

### 6.1 画風はテーマ（色・文字・線の定義）で決める

描く処理は 1 つにし、画風は次の項目を持つテーマファイル（`theme.json`）で切り替える。

| 分類 | 項目 |
|---|---|
| 色 | 背景、文字、補助の文字、線、ノードの種類ごとの色（actor / process / store / external / added / removed / muted）、強調、データ（点・札）、字幕の地と文字 |
| 文字 | 見出し・本文・ラベルのフォント（Google Fonts の名前か、埋め込むフォントファイル）と太さ |
| 形 | 角の丸み、線の太さ、手描きにするか（rough.js の荒さ）、光のぼかし |
| 動き | イージング（3b1b の smooth / 弾む / 直線）と、出し方（線を引く / ふわっと出す） |

最初に用意する画風は、3b1b 調（暗い背景）、手描きのホワイトボード調、フラットな図解（明るい背景・社内資料向け）の 3 つ。

### 6.2 インタビューでの聞き方

画風の問いの選択肢は「3b1b 調」「手描き調」「フラットな図解」「デザインシステムに合わせる」の 4 つにする。AskUserQuestion のプレビューに、同じ場面の静止画（や ASCII の見本）を入れて見比べられるようにする。

「デザインシステムに合わせる」を選んだら、何を渡せるかを聞く。

- **claude.ai の Design System の Artifact**: `tokens.json`（色・文字・角の丸み）を読んでテーマに写す
- **CSS 変数やトークンの JSON ファイル**: 同じくテーマに写す
- **ブランドガイドの PDF や URL**: Claude が色とフォントを読み取ってテーマを作り、どの値をどこから取ったかを `theme.json` の注記に残す

写したあと、テーマを検査するスクリプト（`check_theme.py`）で次を確かめる。

- 字幕・ラベルと背景のコントラスト比が足りているか（WCAG AA）
- ノードの種類ごとの色が見分けられるか
- フォントが Google Fonts にあるか、埋め込めるか

足りないところは、近い色に寄せて直し、直したことを報告する。

### 6.3 配置の検査

v1 は Manim の中で、重なりやはみ出しを機械で検査していた。v2 では、プレーヤーの配置部分を node でも動く共通の JS モジュールにする。

- ELK は node でも同じ結果を返す
- 文字の幅は、テーマのフォントの字幅表を同梱して計算する（ブラウザの計測とずれるので、余白を見込む）
- 検査は claude.ai のサンドボックス（chromium なし）でも動く
- Claude Code では、Playwright でコマの画像も撮って目で確かめられる

## 7. 声

- voicevox_core を Python から直接使う。Docker のエンジンはやめる
  - 導入スクリプト（`setup_voice.py`）が、wheel・ONNX Runtime・辞書・音声モデルを GitHub から取り、`pip install --break-system-packages` で入れる
  - 利用規約への同意は、インタビューで先に取る
- 1 行ずつ合成して保存し、文が変わった行だけ作り直す。1 回のコマンドが長くならないよう、行をまとめて少しずつ回す
- 声と口調はインタビューで決める。非開発者向けの社内資料では「です・ます」の落ち着いた声を勧める。ずんだもんは語尾が「〜のだ」になる
- クレジット（例「VOICEVOX:ずんだもん」）は、画面と再生ページの両方に出す

## 8. プラグインの構成

```
ugoku-zukai/
├─ .claude-plugin/plugin.json       プラグインの定義
├─ .claude-plugin/marketplace.json  単体で入れるためのマーケットプレイス定義（claude plugin marketplace add fm-yodai/ugoku-zukai）
├─ skills/make/                     本体スキル（/ugoku-zukai:make、「動く図解にして」）
│   ├─ SKILL.md            進行役。環境の判定と、両環境の手順
│   ├─ references/         v1 の基準・構成の型・文章の規則（移植済み）。ショット DSL・manim-web.md は M1・M5 で書く
│   ├─ player/             プレーヤー本体（共通 JS）・テーマ（M1）
│   ├─ scripts/            ledger.py・check_contract.py（移植済み）。setup_voice.py・tts.py・lint・check_theme・layout_check・build_player.py（M1〜M3）
│   └─ assets/             禁止語・読みの辞書の初期値（移植済み）
├─ agents/                 researcher / writer / animator / fact-checker / writing-reviewer / director（v1 から移植。Manim 依存の記述は M3 で書き換える）
├─ prototypes/compare/     画風の見比べと SVG プレーヤーの試作
├─ tools/probe/            claude.ai の検証用スキル
├─ tools/build_claude_ai_zip.py   claude.ai 用の zip を作る（frontmatter を name と description だけにする。agents は入れない）
└─ docs/design.md          この文書
```

- **学びの記録**: 使うたびに学んだこと（禁止語・読み・op の提案・較正の例）は `${CLAUDE_PLUGIN_DATA}` に書き、配布する初期値と重ねて読む。claude.ai ではスキルのフォルダに書き込めないので、会話の最後に「足すべき項目」として報告するに留める
- **パス**: スクリプトのパスは `${CLAUDE_PLUGIN_ROOT}/skills/make/...` で書く。エージェントの `tools:` の中でこの変数が展開されるかはドキュメントに書かれていないので、M3 で確かめる。エージェント名には `ugoku-zukai:` の接頭辞が付く

## 12. M1 の要件（2026-11-05 合意）

- **台本の形式はゼロから設計する**。v1 の op・座標・秒の既定値には縛られない。v1 のテスト台本は終わりの条件にしない
- **二層で書く**: 普段は意味（「この図を出す」「この経路をたどる」「ここを強調」）で書き、配置と動きはプレーヤーが決める。足りないところだけ、図形と動きを直接書く下の層を使う。評価役が台本だけで「何を見せるか」を照合できること
- **時間合わせは字幕の文中の印**（例:「{a}課長が承認すると{b}経理へ」）。VOICEVOX が返すモーラ単位の時刻で、印の語を話す瞬間に動きを結ぶ。音声のない M1 では文字数からの見積もりの時刻で動かす
- **図の種類（11）**: M1a = 箱と矢印（構成・業務の流れ・状態遷移、点が経路をたどる）、シーケンス図、表・比較・箇条。M1b = スイムレーン、As-Is / To-Be、ロードマップ、ツリー、グラフと KPI、2×2 マトリクス、ピラミッド・ファネル、サイクル・ベン図。コード・画面写真は M1 に入れない
- **テーマ**: 3b1b 調、フラットな図解、デザインから作る。手描き調は M1 に入れない
- **デザインの入力**: トークンの JSON / CSS 変数、claude.ai の Design System、ブランドガイド（PDF・URL）、Figma など他のツールの書き出し。**デザインシステムらしくない入力**（画像・Web ページ・PowerPoint/PDF/Word・題材のコードの CSS や Tailwind の設定）からも色・文字・形を抽出してテーマにする。抽出したテーマはコントラストなどを検査する
- **画面は 16:9 だけ**
- **字幕は画面の下に出し、再生ページで消せる**。mp4 には書き出すときの設定どおりに入る
- **確認は動くもので**: 仕様書（references/storyboard.md）は書くが、ユーザーの確認は M1a の一覧ページで、台本と絵を並べて行う

### M1a の実装（2026-11-05）

- プレーヤー: `skills/make/player/src/`（util・figures・validate・engine・check・view_svg）。DOM に触るのは view_svg.js だけで、残りは node でも動く。elkjs 0.9.3 は vendor/ に同梱して HTML に埋め込む（claude.ai で CDN を読めるか未確認のため）
- 文字の幅は実測せず、文字の種類から見積もる（フォントの読み込みに左右されず、node の検査と同じ値になる）
- 時刻表がないときは文字数から見積もる（ずんだもん・話速 1.1 で 1 文字 0.17 秒）。M2 の tts は `{ lines: [{ id, start, dur, marks: { 印: 秒 } }] }` を書く
- 検査: `scripts/check_storyboard.cjs`（形・解決・配置）、`scripts/check_theme.py`、`scripts/tests/run_m1.sh`
- デザインの抽出: `scripts/extract_design.py`（トークン JSON・CSS・HTML/URL・Tailwind・Office のテーマ・画像・PDF）。名前のない色だけの入力では役割の割り当てが推測になるので、Claude が確かめて直す
- 見本帳: `tools/build_gallery.py`（見本 5 本 × テーマ 3 種）

## 14. M3 の追加要件（2026-11-09 字幕・読み・チャプター）

### 指摘と原因

1. **日本語として不自然な文が多い**（冒頭の「題材を渡すと、何が起きて再生ページになるのでしょうか」から、初めて見る人には「題材」も「再生ページ」も分からない）。原因は 5 つ
   - インタビューの「一番分かってほしいこと」と契約の言い切りが、作り手の言葉（`ledger.py status` の判定、基準 ID など）のまま書かれ、writer がそれを写した
   - 読者は「これから使う人」なのに、使う人が知らなくてよい内部の仕組み（台帳・基準 ID・周回の判定）を言い切りに選んでいた。視聴者が何を知っていて、見終わって何ができればよいかを誰も確かめていなかった
   - 自然さを誰も見ていなかった。`rules.md` は正確さだけを見て、自然さは別のスキル `japanese-natural-writing` に任せていたが、そのスキルはサブエージェントにも claude.ai にも入っていない
   - `storyboard.md` の `title` 図の説明（「問い・章の扉」）と見本が、問いかけで始める書き方を教えていた
   - TW-5 の直した例が、名詞の前に説明を重ねる形（「外部サービスの障害を表すエラー種別 EXTERNAL で」）を教えていた
2. **読み間違いと、間の空きすぎ**。VOICEVOX は半角スペースのたびに 0.3〜0.7 秒の間を入れる。台本は字幕の慣習で数字や英字の前後を空け、`read` もそれを写していた。「作り手」をツクリシュ、「各行」をカクコウと読んでいた
3. **「未解決の指摘 N 件」をページに出したくない**。視聴者向けのページに作り手の内部の状態を出していた
4. **「根拠」のたたみの中に字幕の一覧が隠れているのが不自然**。一覧の主役は場面と字幕の行で、根拠は添え物

### 決めたこと

- **言葉の 3 層**: 視聴者の言葉で書くのは、インタビュー（`interview.md`）→ 契約の言い切り（`claims[].text`）→ 字幕の 3 か所。進行役はユーザーの答えをユーザーの言葉のまま書く。researcher は言い切りを視聴者の知っている前提で分かる言葉で書き、コードの名前は視聴者が自分で打ったり探したりするものだけ使う（根拠のファイルと行は `source` に置く）
- **`can_do` と `knows`**: インタビューで「見終わったらできること」と「知っている前提」を聞き、`contract.json` の必須の項目にする（`check_contract.py` が求める）。契約の基準に、言い切りが視聴者の言葉で書かれていること・`can_do` に要らない内部の仕組みを言い切りにしていないことを足した（director 構造モード、must）
- **聞いて分かる文の規則（SP-1〜SP-9）**: `references/writing/spoken.md`。冒頭で何の説明かを素直に言う、前提にない語は意味を先に別の文で言う、内部の呼び名は要るときだけ、1 文に 1 つのこと（50 字・並べるのは 3 つまで）、印のために読点を増やさない、「の」を 3 つ続けない、比喩・演出・造語をしない、名詞と動詞の組み合わせを確かめる、直しすぎない。別のスキルには頼らない。あわせて TW-5 の例を文を分ける形に、`title` 図の説明を「題（『〜について説明します』の形でも、問いでもよい）」に直した
- **機械の警告**: `check_text.py` が 1 文 50 字超・「・」3 つ以上・「の」3 つ以上を警告する（SP-4・SP-6）。止めはせず、writing-reviewer が判定の材料にする。writer と writing-reviewer は同じ規則を持ち、writing-reviewer は `interview.md` の視聴者として初めて聞いたつもりで判定する（S-W5〜S-W7）。場面の題と `title` 図の文も見る
- **読み上げの前の整形**: `tts.py` が読む文のスペースを消す。左右が両方とも英数字のときだけ残す（「Claude Code」がつながらないように）。印は取り出して整形後の位置に置き直す。間を入れたいときは `read` に読点を書く。字幕 `text` の表示は今のまま。合成のキャッシュの鍵は整形後の文

- **チャプター一覧と根拠の吹き出し**: 再生ページの「根拠」のたたみをやめ、チャプター一覧を常に出す。幅 960px 以上では図の右、狭ければ再生バーの下。チャプターの題は場面の `title`、なければ図の `title`（`title` 型の図の場面は「はじめに」）。題の無い場面は直前のチャプターに入れ、同じ題が続けば 1 つにまとめる（題の取れない場面が 2 つ以上続くと `check_storyboard.cjs` が警告する）。チャプターと字幕の行を押すとその時刻へ飛び、再生バーにはチャプターの境の刻みを入れる。根拠は行の横の「※」に添え、PC では行にマウスを乗せるかキーボードで移ると吹き出しで出る。タッチの端末では「※」を押して開き、もう一度押すか外を押すと閉じる

## 15. 進め方の作り直し（2026-11-10）

進め方（インタビュー・契約・フェーズの順番・評価役の回し方）を作り直した。プレーヤー・台本の形式・声・機械検査は、ほぼ今のまま使う。設計の全文は、手元の設計メモ（`docs/superpowers/specs/2026-11-10-usui-shinkou-design.md`。git には入れていない）にある。ここには要点と、実装したものを書く。

### なぜ作り直したか

1. **契約の確認が形だけになっていた。** 契約は一枚の大きな文書で、利用者は実際にはほとんど見ずに通していた
2. **資料のない題材を受け止められなかった。** 「資料を取材して正確に写す」ことを軸にしていたので、題目だけを渡されるケースや大きなテーマでは、仕事の大半である「何を語るか」を決める場所がなかった
3. **動画の大きな構成が先に決まっていた。** 構成の型（5 種）のどれかを選び、その型の部の並びに従うことが基準になっていた

きっかけの例は「自社の開発部に、UX とは結局何かと、受託開発のどの段階で要るかを 5 分で説明する動画」。中身は、一般的な知識・自社の事情（利用者の頭の中）・伝えたいこと（利用者にしか決められない）から来る。正しさの物差しは「資料と合っているか」から「利用者の言いたいことと合っているか、視聴者に通じるか」に移る。図の種類は今のもので足り、足りないのは進め方だった。

### 決めたこと（利用者と合意）

- **二層に分ける。** 核は、順番を前提にしない道具（構成メモ・台本・絵コンテ・声・テーマ・評価役と基準・指摘の一覧・組み立て）。その上の `SKILL.md` と環境ごとの文書は薄くし、原則・道具の一覧・必ず守る条件だけを書く。番号の付いたフェーズは持たない
- **構成は会話で固める。** 話題ごとに「聞く・案を出す・調べる」を選ぶ。案を出すときは、他の選択肢を必ず残す。小さな塊で返して合意を積み上げる
- **任せると言われたら、絵コンテまで聞かずに進める。** 見せるのは、絵コンテ・Claude が決めたことの一覧・残った指摘
- **検査は、決定的なものも非決定的なものも残す。** 指摘には must / should / nits のレベルを付けて利用者に見せ、どれを直すかを利用者が選ぶ。台本の初稿に限り、合意した内容を変えない指摘は進行役が 1 回だけ先に直す
- **順番として守るのは 3 つだけ。** 声を合成する前に利用者が絵コンテを見ている／公開する前に機械検査が通っている／must を直さずに公開するときは報告に残論点として書く
- **完成後も、再生ページの箇所（`s2 / l2 @0:14`）を指して直せる。** Claude Code では別のセッションからも直せるようにする。claude.ai は、今回は同じ会話の中だけ（R3 で実装する）

### やめたもの

- 決まった項目のインタビューと `interview.md`、契約 `contract.json` と `check_contract.py`、人の確認 1 回
- 周回の仕組み（最大の周、PASS / CONTINUE / STOP の判定、作り手の応答 `fixed` / `disputed`、振動や反論の打ち切り）
- 構成の型を必須にすること（`structures.md` は章立ての案を出すときの引き出しにした）と、場面の `role`
- 既定の長さ 3 分
- 「進行役は成果物の中身を書かない・指摘の本文を読まない」という約束。守るのは、評価役が作り手や会話から独立していることである

### R1 の実装（2026-11-10。新しい道具を、当時の流れを壊さずに足した）

- **構成メモ** `outline.json`（`references/outline.md`、`scripts/check_outline.py`）: 利用者と合意したことの記録。`basics`（視聴者・前提・持ち帰ってほしいこと・長さ・見た目・声・口調など）と `chapters`（章ごとの言うこと `says`・見せるもの `shows`・尺の目安 `seconds`）を、同じ形の「項目」で持つ。項目には `by`（`user`・`claude`・`source`）と `state`（`proposed`・`agreed`）がある。`--ready` は台本に進める状態（`audience`・`knows`・`takeaway` がある、どの章にも言うことがある）かを見る
- **台本の章**: 場面に `chapter`（構成メモの章の id）を書ける。`check_storyboard.cjs --outline` が構成メモと突き合わせ（場面の `chapter`、章の順、章ごとの見積もりの長さ）、`--complete` を付けると場面のない章を誤りにする。突き合わせを `check_storyboard.cjs` の側に置いたのは、章ごとの長さの見積もりに配置と時刻の計算が要るため
- **一部の場面だけのコマ**: `frames.cjs --scenes`。`frames.json` の行に `start`（行の始まりの時刻）を足した
- **絵コンテのページ** `scripts/build_sheet.py`: 章ごとに区切り、各行のコマ（SVG を `data:` の画像として埋め込む）の横に `s2 / l2 @0:14` と字幕の全文を並べた HTML 1 枚。`--outline` があれば、終わりに「Claude が決めたこと」（`proposed` の項目）を出す。コマが今の台本のものでなければ、書かずに止まる

### R2 の実装（2026-11-10。進め方を切り替えた）

- **指摘の一覧** `scripts/ledger.py`: 周回の判定をやめ、指摘のレベル・誰が直すと決めたか・再確認の結果を記録する。状態は `open`（未対応）・`fixing`（直すと決めた）・`kept`（利用者が直さないと決めた）・`closed`（再確認で通った）。コマンドは `ingest`・`decide`・`list`・`status`・`residual`。`list` は must を全文、should を 1 件 1 行、nits を件数だけで出す
- **成功基準** `references/criteria/`: 契約の基準（C-）を構成メモの基準（O-。`outline.md`）に替え、台本と構成メモの照合（A-。`agreement.md`）を足した。口調が構成メモの `tone` に合うか（S-W10）と、出どころのない事実の記述（O-F3・S-F4）を足した。使わなくなった ID（C- のすべて、S-F3、S-D3）は欠番にし、移り先を `README.md` に書いた
- **評価役の約束** `references/review-protocol.md`（`loop-protocol.md` の後継）: 評価役の独立、判定の約束、指摘の扱い（見せ方、初稿の先直し、利用者の選択、残論点）。評価役どうしが食い違ったときの順は「事実 > 合意 > 構造 > 文章 > 演出」
- **エージェント** `agents/`: researcher は調べて取材メモを書く役にした（構成メモは書かない）。writer は構成メモを物差しに、台本の初稿と章単位の書き直しを受け持つ。評価役 3 つは `target`（`outline`・`script`・`screen`・`voice`）で呼び、指摘にレベルを付け、渡されたキーだけを再確認する
- **進行役の文書**: `SKILL.md` を原則・道具の一覧・必ず守る条件に、`run-code.md`・`run-chat.md` を道具ごとのコマンドと環境の約束に書き直した
- **検査**: `scripts/tests/run_r2.sh`（指摘の一覧・基準・エージェント・進行役の文書）→ `run_r1.sh`（構成メモ・台本の章・絵コンテ）→ `run_m3.sh`（核の検査）→ `run_m1.sh` の順に呼ぶ

### R3 の実装（2026-11-10。公開した後の直しと声の試聴の道具。通しはまだ）

- **再生ページの「直したい箇所を指す」** `player/template.html`: 開くと、今の位置が `s2 / l2 @0:14`（場面 / 行 @時刻）で出て、コピーできる。「ここを範囲の始まりにする」を押して進めると、`s2 / l2 @0:14 〜 s3 / l5 @0:41` の範囲になる。表記は絵コンテのページの行と同じ。コピーは、クリップボードの API → `execCommand` → 文字を選択して残す、の順に試す（Artifact は iframe の中で動き、クリップボードが拒否されることがあるため）。声なしの粗い再生ページにも同じものが出る
- **公開先の記録と作業フォルダの一覧** `scripts/workdir.py`: `publish` が `<workdir>/published.json`（題・URL・テーマ・題材の場所・最初と最後の公開の時刻・回数）を書き、`list` が過去の作業フォルダを新しい順に出す。Claude Code で、公開したのと別のセッションから直すときに使う。claude.ai では使わない（会話をまたいで作業フォルダが残らない）
- **絵コンテのページ** `scripts/build_sheet.py`: 構成メモの `open` を「まだ決めていないこと」として終わりに出す。`frames.cjs` が `frames.json` に時刻の出どころ（`timed`）を書き、合成した声の時刻で作ったコマなら、頭の表記を「時刻は合成した声に合わせたもの」にする（図だけを直した場面を見せるとき、時刻が再生ページと同じになる）
- **声の試聴** `scripts/tts.py --audition 8,2,3 [--sample "文"] [--artifact]`: 候補の話者に同じ 1 文を読ませ、聞き比べるページ `voice/audition.html` を書く。WebAudio で鳴らし、VOICEVOX のクレジットを出す。文は `--sample` か台本の最初の行で、`--sample` があれば台本は要らない
- **進行役の文書**: `SKILL.md` に「公開した後の直し」（箇所の受け取り方、流れ、直すものごとの作り直すものと評価役）を足し、`run-code.md`・`run-chat.md` にコマンドと、別のセッションから直す手順を書いた
- **検査**: `scripts/tests/run_r3.sh` が `run_r2.sh` に続けて、位置の表示・作業フォルダ・声の試聴・直しの文書を検査する。VOICEVOX が手元にあれば、声の試聴と、直した後の声の使い回し（変えた行だけが作り直されること）も確かめる

設計書から広げたこと（実装のときに決めた。違っていれば直す）:

- **位置の表示は、ふだん畳んでおく**（`<details>`）。再生ページは視聴者にも配るので、開いたときだけ出す
- **公開先の記録に、テーマと題材の場所も持たせた**。設計書は URL と題だけだが、別のセッションで組み立て直すにはテーマが、評価役を呼ぶには題材の場所が要る
- **作業フォルダの一覧は、置き場を複数探す**（`UZ_RUNS_HOME`、`${CLAUDE_PLUGIN_DATA}/runs`、その隣の `ugoku-zukai*` の `runs`、`~/.cache/ugoku-zukai/runs`）。プラグインの入れ方が変わると `CLAUDE_PLUGIN_DATA` が変わるためである
- **直しの表に「見てもらう評価役」の列を足した**。設計書の表は、作り直すものだけを書く。読みの直しは、言い回しの直しと行を分けた
- **公開の記録がない作業フォルダ**（この仕組みより前に作ったもの）は、一覧に「未公開」と出る。直すときは、URL とテーマを利用者に聞いて記録してから進める
- **直しで出た評価役の指摘は、先に直さない**。先に直すのは初稿だけなので、いつものとおり利用者に見せて選んでもらう

### 設計書から広げた判断（R2 の実装で決めた。利用者の確認待ち）

設計メモに書いていなかった場合を、実装のときに決めた。違っていれば直す。

- **先に直す範囲**: 設計メモは「初稿に限り 1 回だけ」と書く。実装では、台本の初稿の評価（`script`）と、その台本の最初の絵コンテの評価（`screen`）を対象にした。読みの一覧の最初の評価（`voice`）も、合意した内容を変えないので、進行役が 1 回だけ先に直す
- **任されているときの、構成メモの段階の指摘**: 利用者に見せる機会がないので、自分で決めた項目（`proposed`）の言い回しと出どころを直す指摘は先に直し、言うことを足す・削る、章を変える指摘は絵コンテと一緒に見せる
- **漏れ（O-F2）の「資料のある題材」**: 利用者が渡した資料を説明する動画に限る。題目だけを受け取り、進行役が調べて集めた資料は数えない
- **出どころのない事実（O-F3・S-F4）は should**: 調べて出どころを付けるか、利用者の考えとして言うか、そのまま通すかを利用者が選ぶ。S-F4 は、利用者の言うことを言い換えた行は見ず、台本が足した具体例や数値は利用者の章でも見る
- **利用者の言葉（`by: user`）には禁止語の警告を出さない**（字幕に出たら `check_text.py` が誤りにする）
- **評価役どうしが食い違ったときの順に「合意」を足した**（事実 > 合意 > 構造 > 文章 > 演出）
- **図の区分の境界（G-D6）は director だけが見る**。前は fact-checker が境界の根拠を資料で確かめていたが、今は確かめる役がない
- **指摘の一覧の守り**: 作業フォルダがない・評価役の出力の形が崩れているときは、何も書き換えずに止まる。FAIL なのに指摘のない基準は must の指摘にする。利用者が直さないと決めた指摘は、進行役が直すと決め直せない。直さないと決めた指摘のレベルが上がったら、未対応に戻す

### 残り（R3）

- 終わりの条件の通し: 任せると言われた 1 本、このリポジトリの紹介（資料のある題材）、UX の動画（題目と利用者の頭の中から）を、Claude Code で最後まで作る。少なくとも 1 本は claude.ai でも作る。M3 に残っていた「両環境での通し」はここに含める
- 直しの通し: 公開したページの 1 行と 1 範囲を指して、Claude Code の別のセッションから直す。変えていない行の声が作り直されないことを確かめる
- 確かめること: エージェントをサブエージェントとして実際に呼べるか。絵コンテのコマ（`data:` の SVG 画像）が claude.ai の Artifact で表示されるか。claude.ai で、「直したい箇所を指す」のコピーが Artifact の中で効くか、Artifact のコメントを会話の Claude が読めるか。Web 検索が使えるときと使えないときの振る舞い。5 分の台本で、絵コンテの枚数と評価役に見せる量が重すぎないか
