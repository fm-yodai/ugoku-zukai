# 評価役の約束と、指摘の扱い

作り手（進行役・researcher・writer）が作ったものを、評価役（fact-checker・writing-reviewer・director）が `criteria/` の基準で判定する。評価役が見るのは、**意図どおりのスライド・原稿になっているか**である。物差しは、構成メモの意図（章の順番の意図、章の意図とつながり、スライドの意図とつながり）で、意図そのものが聴衆の側から書いてあるかも見る。評価役は、決まった順番の関門ではなく、必要な場面で進行役が呼ぶ。指摘をどれから直すかは利用者が決める。自動で合格まで回し続けることはしない。

評価役の出力の形は `writing/review-format.md`、指摘の一覧は `scripts/ledger.py`（`<workdir>/review/ledger.json`）が正。

## 評価役を呼ぶ場面

作る順番は、意図 → スライド → 原稿である。評価役も、この順に呼ぶ。担当の基準は `criteria/README.md` の表にある。

| 呼ぶ場面 | 見るもの | 評価役（`target`） |
|---|---|---|
| 章の意図が固まったとき | 構成メモ。意図が聴衆の側から書いてあるか、意図をたどると持ち帰ってほしいことに届くか、資料の要点の漏れ | director（`outline`）。資料のある題材なら fact-checker も（`outline`） |
| 最初のスライドコンテを見せる前 | スライド。意図どおりの 1 枚か、声と字幕がなくても資料として読めるか、並びがつながりの意図どおりか。行ごとのコマ | director（スライドは `script`、コマは `screen`） |
| スライドが固まった後 | 原稿。スライドとその意図どおりか、スライドを説明しているか、文章の規則、出どころ。スライドのテキストに書かれた事実 | writing-reviewer と fact-checker（`script`）。スライドを変えていたら、director に変えたスライドだけ |
| 直した後 | 直した項目の再確認と、変えた章・スライド・行だけ | 指摘を出した評価役（元と同じ `target`） |
| 合成の前 | 読みの一覧 | writing-reviewer（`voice`。読みモード） |

- 原稿を writing-reviewer と fact-checker に細かく見せるのは、利用者がスライドコンテを見て、スライドが固まった後である。先に原稿を細かく直すと、スライドを変えたときに無駄になる
- 最初のスライドコンテにも原稿の初稿は付いている。director は、意図に書かれたことの在りかを探すときだけ原稿を読む。原稿の言い回しは見ない
- 利用者が続けて細かく直している間は、機械検査だけを回す。スライドコンテを見せ直す前か、合成の前に、まとめて評価役を呼ぶ

## 評価役の独立

評価役は、作り手とも利用者との会話とも切り離して判定する。聴衆も、作り手の推論や会話の経緯を知らないからである。

- **渡すもの**: 作業フォルダ（構成メモ `outline.json`・台本 `storyboard.json`・コマ `frames/`（行ごとのコマと、スライドの完成形のコマ）・読みの一覧）、題材の資料の場所、`target`、基準のファイル、再確認するキーの一覧、見る範囲（章や行の id）、出力先
- **渡さないもの**: 利用者との会話、作り手の推論や下書きの経緯、取材メモ `brief.md`（fact-checker は資料そのものを読む。取材の段階の誤りも拾うため）

構成メモは、利用者と合意した結果なので渡す。評価役は、構成メモの意図を物差しにしてスライドと原稿を見る。ここでいう意図は、構成メモに書かれた文のことである。作り手が頭の中で考えた狙いは、構成メモに書かれていなければ物差しにしない。

## 評価役の約束

- **基準 ID ごとに判定する**（`checks`）。担当の基準をすべて PASS / FAIL / UNKNOWN のどれかにする。判定しない基準を残さない
- **重さは基準の表に従う**。重さが must だけの基準の指摘を should や nits にしない（`ledger.py` が must に直して取り込む）
- **根拠のない判定は無効**（`ledger.py` が捨てて警告する）。FAIL は場所と引用、PASS は確認した範囲
- **意図に照らした判定には、意図のどの文に照らしたかを書く。** `evidence` に、意図の場所（章 `c2` の `intent`、スライド `ux-def` の `link`、`flow`、`basics.knows`）と、その文の引用を入れる。意図に照らす基準は数では決まらず、評価役によって判定がぶれることがある。それは受け入れるが、何に照らしたかは、利用者が読んで判断できるように必ず残す
- **再確認は渡されたキーだけ**（`rechecks`）。渡されたキーは、すべて PASS か FAIL で返す
- **見る範囲を渡されたら、その範囲だけを判定する**。範囲の外の基準は、前の判定のままにする
- **担当外の基準は判定しない**
- **意図そのものも見る。** 意図が聴衆の側から書かれていない、聴衆が知らない語を前提にしている、と判定したら、指摘として出す（O-D・A-5）。意図を自分で読み替えて、スライドや原稿を判定しない
- **スライドは資料として、原稿はその説明として見る。** スライドの見出しと字幕の言い回しが違うことは、指摘しない。スライドのテキストには、書き言葉の規則（TW-）だけをかける
- 衝突したときは **事実 > 合意 > 構造 > 文章 > 演出** の順で上を採る。「合意」は、利用者と合意した意図を指す。下の指摘が上の基準と矛盾するなら、進行役は上を採り、下の指摘は利用者に見せるときに理由を添える
- 書き換えはしない。直し方は `suggestion` に書く

## 指摘の扱い

1. **機械検査を先に回す。** `check_outline.py`・`check_storyboard.cjs`・`check_text.py` の誤りは、評価役を呼ぶ前に直す。答えが一つに決まる不具合（図のはみ出し・重なり、id の解決、印の誤り、禁止語、古くなった音声）は、利用者に聞かずに進行役が直し、直したことを報告する。Claude Code では「機械検査の差し戻し」として、検査の出力だけを writer に渡して直させてもよい。機械検査の誤りは指摘の一覧に載せない
2. **取り込む。** 評価役の出力を `python3 scripts/ledger.py ingest <workdir> <出力 …>` で指摘の一覧に入れる。進行役は指摘の本文を読む（利用者に見せるのが進行役だからである）
3. **スライドと原稿の初稿に限り、意図を変えない指摘は、進行役が 1 回だけ先に直す。** 初稿では指摘が多く、そのまま見せると利用者は選びきれない。対象は、最初のスライドコンテを見せる前の評価（スライドの `script` と、コマの `screen`）と、スライドが固まった後の、原稿の初稿の評価（`script`）である。読みの一覧の最初の評価（`voice`）も、同じ理由で 1 回だけ先に直す。意図を変えない指摘とは、合意した内容を変えずに直せる指摘のことで、言い回し、読み、スライドの見やすさ（区画、テキストの量、見出しの書き方、至り方の細部）、出どころを調べて付けることがこれに当たる。直すと構成メモの意図（`flow`・`intent`・`link`）・章の順・利用者が見て決めたスライドの切り方が変わる指摘は、直さずに見せる。スライドの意図（`proposed` のもの）を書き換えないと直せない指摘も、直さずに見せる。`ledger.py decide <workdir> --by lead --fix <キー …>` で記録し、直したら同じ評価役に再確認を 1 回だけ頼む。通らなかったものは、それ以上回さずに利用者に見せる。任されているときは、構成メモの評価（章の意図が固まったとき）で出た指摘も同じに扱う。自分で決めた項目（`proposed`）の言い回しを直す指摘は先に直して再確認を 1 回頼み、意図の中身を変える、章を変える指摘は直さずに、スライドコンテと一緒に見せる
4. **レベル順に見せて、どれを直すかを聞く。** `ledger.py list <workdir>` の出力をそのまま使う（must は全文、should は 1 件 1 行、nits は件数だけ。求められたら `--full` で開く）。先に直したものがあれば、`ledger.py list <workdir> --by lead` で件数と中身も見せる
5. **利用者の選択を記録して直す。** 直すものは `decide --by user --fix <キー …>`、直さないものは `decide --by user --keep <キー …>`。直しが意図に関わるなら、先に構成メモを直してから、スライド、原稿の順に直す。直したら、同じ評価役に、直した項目のキーと変えた章・スライド・行だけを渡して再確認を頼み、`ingest` する。スライドの直し方が 1 つに決まらないときは、進行役が案を並べて利用者に選んでもらう（`scripts/alts.py`）
6. **must を直さずに公開するときは、残論点として報告する。** `ledger.py residual <workdir>` が、must で直っていない指摘を `review/residual.md` に書く。最後の報告に必ず出す（再生ページには出ない）。黙って公開しない

利用者が続けて細かく直している間は、機械検査だけを回す。スライドコンテを見せ直す前か、合成の前に、まとめて評価役を呼ぶ。評価役が見た後に、作り手が自分で構成メモや台本を変えたときも同じで、次に呼ぶときに、変えた項目・スライド・行を見る範囲として渡す。

指摘の状態は 4 つ: `open`（未対応）、`fixing`（直すと決めた。再確認を待っている）、`kept`（利用者が直さないと決めた）、`closed`（再確認で通った）。直さないと決められるのは利用者だけである。

- **直し中のまま残さない。** 再確認を頼まずに済ませた指摘（評価役の見落としだった、利用者が自分の言葉で直した）は、`ledger.py decide <workdir> --by lead --close <キー …> --note <理由>` で閉じる。must を再確認なしで閉じられるのは、利用者が見て通したときだけ（`--by user`）。利用者が指摘とは違う直し方を選んで直したときは、`--fix` を挟まずに `--by user --close` で閉じてよい（未対応の指摘も閉じられる）。公開の前に `ledger.py status` で「直し中 0」を確かめる
- **同じ箇所の指摘は、まとめて見せる。** `ledger.py list` が「同じ箇所に <キー>」と添えた指摘は、評価役どうしで直し方が食い違っていることがある。両方を満たす直し方を 1 つにまとめてから見せる（食い違うときの順は、事実 > 合意 > 構造 > 文章 > 演出）
- **文の案をそのまま入れない。** 文章の評価役は事実を見ていない。案が主張の範囲を変えていないか（限定を外して広げていないか、スライドにも意図にもない主張を足していないか）を進行役が見てから入れる。範囲が変わるなら、事実の評価役に見る範囲として渡す

## 作り手の約束

- 基準のファイルを読んでから作る。渡す前に、自分で基準を 1 つずつ点検する（自己点検は評価役の代わりにはならない。漏れを減らすため）
- **意図 → スライド → 原稿の順に作る。** スライドは、声と字幕がなくても資料として読める 1 枚にする。原稿は、そのスライドを説明する文にする。スライドを原稿に合わせて作らない
- **行・場面・章・スライドの id を振り直さない**。行を消したら欠番のままにし、足すときは場面の末尾の番号を使う。指摘のキーは id なので、振り直すと前の指摘と今の行が食い違う（`ledger.py status` が、今の台本にも構成メモにもない id を指す指摘を警告する）
- 直すときに、閉じた項目を壊していないかを確かめる。章や全体を書き直すときは、先に閉じた指摘を読み、その行で直した言い回しを保つ
- 頼まれた範囲だけを直す。章の書き直しでは、ほかの章の行の文と id を変えない
- スライドとコマの指摘は、スライドの宣言と動作で直す。字幕を変えないと直せないときは、その直しが意図を変えるかを進行役が見て、変えるなら利用者に見せる
- 意図（構成メモの `flow`・章の `intent`・`link`）を書き換えるのは進行役で、決めるのは利用者である。writer が構成メモに書くのは、自分が切ったスライドの意図（`proposed`）だけである

## チャットでの回し方

claude.ai のチャットではサブエージェントを起動できないので、1 つの会話で作り手と評価役を順に演じる。指摘の一覧は Claude Code と同じ `ledger.py` を使い、次の点だけを変える。

- **評価役の番の始めに宣言する。** 「ここからは評価役として、作り手の推論と利用者との会話を使わず、基準のファイル・資料・構成メモ・台本（スライドと原稿）・コマだけで判定する」と書いてから判定に入る。取材メモ（`brief.md`）と、作り手として考えた理由は判定の根拠にしない
- **評価役は、呼ぶ場面ごとに 1 回にまとめる。** 呼ぶ場面は上の表と同じである（章の意図が固まったとき、最初のスライドコンテを見せる前、スライドが固まった後、直した後、合成の前）。その場面の評価役の担当をすべて 1 回で判定し、全基準の判定を 1 つのファイル `<workdir>/review/<連番>-<target>/combined.json` に書く。形は評価役の出力と同じで、`reviewer` は `combined`
- スライドを見る番（最初のスライドコンテを見せる前）では、字幕を読む前に、スライドの完成形だけを見て「この 1 枚が何を言っているか」を書き出す。作り手として書いた字幕を先に読むと、字幕がなくても読めるかを判定できなくなる
- 機械検査、指摘の見せ方、利用者の選択、残論点の扱いは Claude Code と同じ

## 設計の根拠

Anthropic「Harness design for long-running application development」（独立した懐疑的な評価役・基準ごとの合否）、「Demystifying evals for AI agents」（次元ごとのルーブリック・Unknown を許す）、Huang ら ICLR 2024（自己修正は外部の信号があるときに効く → 機械検査を先に回す）。

直すかどうかを利用者が決める形にしたのは、合格するまで自動で回す形では、利用者が見ないまま内容が決まっていたためである。

物差しを意図にしたのは、章ごとの内容の一覧を物差しにしていたときに、スライドが字幕をなぞり、内容の一覧を利用者がほとんど見ていなかったためである。意図に照らす判定は、数で決まる判定よりぶれやすい。利用者は、柔軟に作れることと引き換えに、これを受け入れると決めた。
