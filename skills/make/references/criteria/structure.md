# 図の基準（G-）— Phase 2 台本・Phase 4 画面

対象は図（`storyboard.json` の `map` と、それを動かす ops）。図の型は `map.kind` の 3 つ（`layered` 層で区切る構成図 / `sequence` シーケンス図 / `state` 状態遷移図）。配置は ELK と解釈器が決めるので、座標の良し悪しは機械検査に任せ、checker は**意味の構造**を見る。記法の項目は C4 モデルの記法チェックリスト（https://c4model.com/diagrams/notation）に倣う。

| ID | 合格の条件 | 検査 | 重さ |
|---|---|---|---|
| G-M1 | 図に題（`map.title`）があり、何の図かが分かる | 機械（lint） | must |
| G-M2 | すべての辺に label がある | 機械（lint） | must |
| G-M3 | layered では全ノードがちょうど 1 つの層に属する | 機械（lint） | must |
| G-M4 | 点は宣言した辺の上だけを動く（VG-9） | 機械（lint） | must |
| G-M5 | 画面で、辺が無関係の箱を貫かず、文字と箱が重ならない | 機械（layout_report の E・`line_on_box`） | must |
| G-D1 | **復元テスト**: 図（map と ops）だけを見て「何がどこからどこへ、どの順で流れるか」を言葉で書き出すと、契約の `paths` と一致する。checker は字幕を読む前に復元を書き、`evidence` にその文を残す | director（計画モード） | must |
| G-D2 | 図の型が契約の `diagram.type` と一致し、その場面で見せたいことに合っている（往復の順序を構成図の点の移動だけで見せていない 等） | director（計画モード） | must |
| G-D3 | 辺の label が具体的な動詞句（「公開鍵を取得」「プロファイルを作成」）で、「使う」「呼ぶ」の 1 語ではない | director（計画モード） | should |
| G-D4 | 線は一方向。応答は別の矢印（`respond` / `msg` の `reply`）で描き、1 本の双方向矢印にしない | director（計画モード） | should |
| G-D5 | 色の意味が図をまたいで一貫し、凡例で説明できる（VG-2。正常な応答を「消えた・失敗」の赤で描かない） | director（計画モード・画面モード） | should |
| G-D6 | 層の分け方が実際の配置・責務の境界（クライアント / 入口 / アプリケーション / 認証基盤 / データ 等。概念の図なら要素の分類の境界）に合っている | director（計画モード）＋ fact-checker（境界の根拠） | should |

## 較正の例

- **全体像が構造的でない**（過去の指摘「整理されているようでそこまで構造的に整理されていない」）: 箱が格子に並ぶだけで層の区切りが無く、1 つの箱だけ半段ずれ、矢印が箱の角から斜めに出る。認証基盤が公開する鍵（JWKS）が、認証基盤の中ではなく独立した箱になっていた → G-M3・G-M5・G-D6
- **点が中途半端な場所を行き来する**（過去の指摘）: 点が箱の名前の文字の上に止まる → G-M5（解釈器が止まる位置を決める）
- **応答が赤**（過去の画面レビュー）: 認証基盤からの認可コード・アクセストークンの戻り矢印が赤で、失敗に見えた → G-D5
