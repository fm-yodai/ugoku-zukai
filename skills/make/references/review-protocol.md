# 評価役の約束と、指摘の扱い

作り手（進行役・researcher・writer）が作ったものを、評価役（fact-checker・writing-reviewer・director）が `criteria/` の基準で判定する。評価役は、決まった順番の関門ではなく、必要な場面で進行役が呼ぶ（呼ぶ場面と担当の基準は `criteria/README.md`）。指摘をどれから直すかは利用者が決める。自動で合格まで回し続けることはしない。

評価役の出力の形は `writing/review-format.md`、指摘の一覧は `scripts/ledger.py`（`<workdir>/review/ledger.json`）が正。

## 評価役の独立

評価役は、作り手とも利用者との会話とも切り離して判定する。視聴者も、作り手の意図や会話の経緯を知らないからである。

- **渡すもの**: 作業フォルダ（構成メモ `outline.json`・台本 `storyboard.json`・コマ `frames/`・読みの一覧）、題材の資料の場所、`target`、基準のファイル、再確認するキーの一覧、見る範囲（章や行の id）、出力先
- **渡さないもの**: 利用者との会話、作り手の推論や下書きの経緯、取材メモ `brief.md`（fact-checker は資料そのものを読む。取材の段階の誤りも拾うため）

構成メモは、利用者と合意した結果なので渡す。評価役は構成メモを物差しにして台本を見る。

## 評価役の約束

- **基準 ID ごとに判定する**（`checks`）。担当の基準をすべて PASS / FAIL / UNKNOWN のどれかにする。判定しない基準を残さない
- **重さは基準の表に従う**。重さが must だけの基準の指摘を should や nits にしない（`ledger.py` が must に直して取り込む）
- **根拠のない判定は無効**（`ledger.py` が捨てて警告する）。FAIL は場所と引用、PASS は確かめた範囲
- **再確認は渡されたキーだけ**（`rechecks`）。渡されたキーは、すべて PASS か FAIL で返す
- **見る範囲を渡されたら、その範囲だけを判定する**。範囲の外の基準は、前の判定のままにする
- **担当外の基準は判定しない**
- 衝突したときは **事実 > 合意 > 構造 > 文章 > 演出** の順で上を採る。下の指摘が上の基準と矛盾するなら、進行役は上を採り、下の指摘は利用者に見せるときに理由を添える
- 書き換えはしない。直し方は `suggestion` に書く

## 指摘の扱い

1. **機械検査を先に回す。** `check_outline.py`・`check_storyboard.cjs`・`check_text.py` の誤りは、評価役を呼ぶ前に直す。答えが一つに決まる不具合（図のはみ出し・重なり、id の解決、印の誤り、禁止語、古くなった音声）は、利用者に聞かずに進行役が直し、直したことを報告する。Claude Code では「機械検査の差し戻し」として、検査の出力だけを writer に渡して直させてもよい。機械検査の誤りは指摘の一覧に載せない
2. **取り込む。** 評価役の出力を `python3 scripts/ledger.py ingest <workdir> <出力 …>` で指摘の一覧に入れる。進行役は指摘の本文を読む（利用者に見せるのが進行役だからである）
3. **初稿に限り、進行役が 1 回だけ先に直す。** 台本の初稿では指摘が多く、そのまま見せると利用者は選びきれない。合意した内容を変えない指摘（言い回し、読み、図の見やすさ、出どころを調べて付けること）は、進行役が先に直す。直すと構成メモの言うこと（`says`）・見せるもの（`shows`）・章の順が変わる指摘は、直さずに見せる。`ledger.py decide <workdir> --by lead --fix <キー …>` で記録し、直したら同じ評価役に再確認を 1 回だけ頼む。通らなかったものは、それ以上回さずに利用者に見せる
4. **レベル順に見せて、どれを直すかを聞く。** `ledger.py list <workdir>` の出力をそのまま使う（must は全文、should は 1 件 1 行、nits は件数だけ。求められたら `--full` で開く）。先に直したものがあれば、`ledger.py list <workdir> --by lead` で件数と中身も見せる
5. **利用者の選択を記録して直す。** 直すものは `decide --by user --fix <キー …>`、直さないものは `decide --by user --keep <キー …>`。直したら、同じ評価役に、直した項目のキーと変えた章・行だけを渡して再確認を頼み、`ingest` する
6. **must を直さずに公開するときは、残論点として報告する。** `ledger.py residual <workdir>` が、must で直っていない指摘を `review/residual.md` に書く。最後の報告に必ず出す（再生ページには出ない）。黙って公開しない

利用者が続けて細かく直している間は、機械検査だけを回す。絵コンテを見せ直す前か、合成の前に、まとめて評価役を呼ぶ。

指摘の状態は 4 つ: `open`（未対応）、`fixing`（直すと決めた。再確認を待っている）、`kept`（利用者が直さないと決めた）、`closed`（再確認で通った）。直さないと決められるのは利用者だけである。

## 作り手の約束

- 基準のファイルを読んでから作る。渡す前に、自分で基準を 1 つずつ点検する（自己点検は評価役の代わりにはならない。漏れを減らすため）
- **行の id と章の id を振り直さない**。行を消したら欠番のままにし、足すときは場面の末尾の番号を使う。指摘のキーは id なので、振り直すと前の指摘と今の行が食い違う（`ledger.py status` が、今の台本にも構成メモにもない id を指す指摘を警告する）
- 直すときに、閉じた項目を壊していないかを確かめる
- 頼まれた範囲だけを直す。章の書き直しでは、ほかの章の行の文と id を変えない
- 絵コンテの指摘は、図の宣言と動作で直す。字幕を変えないと直せないときは、その直しが合意した内容を変えるかを進行役が見て、変えるなら利用者に見せる

## チャットでの回し方

claude.ai のチャットではサブエージェントを起動できないので、1 つの会話で作り手と評価役を順に演じる。指摘の一覧は Claude Code と同じ `ledger.py` を使い、次の点だけを変える。

- **評価役の番の始めに宣言する。** 「ここからは評価役として、作り手の推論と利用者との会話を使わず、基準のファイル・資料・構成メモ・台本だけで判定する」と書いてから判定に入る。取材メモ（`brief.md`）と、作り手として考えた理由は判定の根拠にしない
- **評価役は 1 回にまとめる。** その場面の評価役の担当をすべて 1 回で判定し、全基準の判定を 1 つのファイル `<workdir>/review/<連番>-<target>/combined.json` に書く。形は評価役の出力と同じで、`reviewer` は `combined`
- 機械検査、指摘の見せ方、利用者の選択、残論点の扱いは Claude Code と同じ

## 設計の根拠

Anthropic「Harness design for long-running application development」（独立した懐疑的な評価役・基準ごとの合否）、「Demystifying evals for AI agents」（次元ごとのルーブリック・Unknown を許す）、Huang ら ICLR 2024（自己修正は外部の信号があるときに効く → 機械検査を先に回す）。

直すかどうかを利用者が決める形にしたのは、合格するまで自動で回す形では、利用者が見ないまま内容が決まっていたためである（`docs/design.md` の 15 章）。
