# 原稿の基準（S-）

対象は、台本（`storyboard.json`）の原稿（場面 `scenes` の各行の字幕 `text`・読み `read`・根拠 `source`・動作 `do`）と、スライドのテキストに書かれた事実である。形式は `../storyboard.md` が正。原稿の文章と事実（S-W・S-F）は、スライドが固まった後に判定する（`target` は `script`）。先に原稿を細かく直すと、スライドを変えたときに無駄になるためである。動作の基準（S-D）は、最初のスライドコンテを見せる前に、director が `structure.md`（G-）・`agreement.md`（A-）と合わせて判定する。S-W8・S-W9 は合成の前に、読みの一覧で判定する（`target` は `voice`）。

**原稿は、スライドを説明する文である。** スライドは、声と字幕がなくても読める資料として先に作ってある。原稿は、聴衆がそのスライドのどこを見ればよいか、部品どうしがどういう関係か、なぜそう言えるかを、声で説明する。スライドの文字を上から読み上げるものではない。スライドの見出しと字幕の言い回しを合わせることは求めない。

文章の規則のかけ方は、対象で分かれる。字幕と読みには、書き言葉の規則（TW-）と話し言葉の規則（SP-）の両方をかける。スライドのテキスト（見出し・言いたいこと・テキストの部品）は書き言葉なので、TW- だけをかける（S-W1・S-W2）。

| S-W6 | 冒頭の 1 行目と、最初のスライド（章扉なら `title` 図の文）で、何の説明かが分かる（SP-1。`../writing/spoken.md`） | writing-reviewer | must |
| S-W7 | 聞いて分かる文の規則（`../writing/spoken.md` の SP-。話の流れ SP-11〜SP-14 は S-W11 で見る）に反していない。スライドのテキストには当てない（書き言葉のため） | writing-reviewer | must（意味が取れない・誤解する）/ should（もっと自然にできる） |
| S-W8 | 読みの一覧（`voice/readings.md`）で、意味が変わる読み違いが無い（例: 作り手→ツクリシュ） | writing-reviewer（読みモード） | must |
| S-W9 | 読みの一覧で、語の途中や助詞の前に不自然な間が無い。読点の区切りが続いて遅くなっていない（「間」の列で「、」が 4 つ以上の行は、見る手がかり。数字を 1 桁ずつ読ませる所は、`read` の読点を中黒に替えると短くなる） | writing-reviewer（読みモード） | should |
| S-W10 | 口調が構成メモの `basics.tone` に合っている。`tone` がなければ対象外 | writing-reviewer | must（全体の口調が違う）/ should（一部の文だけ違う） |
| S-W11 | 字幕を上から順に通して読んで、話がつながっている。隣り合う行が受け合い、章が変わるところで、なぜ次の話になるのかが分かり、動画の終わりで持ち帰ってほしいことに届く（SP-11〜SP-14。`../writing/spoken.md`。章の頭の問いや章ごとのまとめは、つながりを作る手段の 1 つで、無いことだけでは FAIL にしない） | writing-reviewer | must（話が飛んで、なぜ次の話になるのかが分からない）/ should（つながるが、ぶつ切りに聞こえる） |
| S-W12 | 原稿が、スライドとその意図どおりである。場面ごとに、その場面が指すスライド（見出し・言いたいこと・部品）と、構成メモのスライドの意図・章の意図を読み、その場面の字幕と比べる。次のどれかなら FAIL。(1) 字幕が、スライドにも意図にもない主張を足している（つなぎの文と、スライドを説明するための具体例は数えない）。(2) 字幕が、スライドに書いてあることと食い違うことを言っている（スライドは「3 段階」、字幕は「4 つの手順」）。(3) 意図に書かれた「聴衆が分かること」のうち、スライドに出ていないものを、字幕も言っていない | writing-reviewer | must |
| S-W13 | 原稿が、スライドを説明している。スライドの文字をただ読み上げていない。場面ごとに、字幕とスライドのテキスト（見出し・言いたいこと・テキストの部品）を並べて読む。字幕が、スライドの文を語尾だけ変えて上から順に読んでいるだけなら FAIL。合格する原稿は、スライドのどこを見ればよいかを言う、部品どうしの関係を言う、なぜそう言えるかを言う、スライドに書いていない具体例で補う、のどれかをしている。定義や引用の囲みを、引用としてそのまま読む 1 行は、読み上げに数えない。逆に、スライドに出ているものにまったく触れず、画面と関係なく話が進む場面も FAIL | writing-reviewer | must（場面の字幕のほとんどが読み上げで、声が要らない。または、字幕がスライドと関係なく進む）/ should（一部の行が読み上げになっている） |
| S-F1 | `source` のある行の主張が、その `source` から言える（FC-wrong / FC-overclaim / FC-nosource が無い） | fact-checker | must |
| S-F2 | 図の宣言（部品として置いた図の辺・メッセージ・表やグラフの値）と動作（`trace`・`reply` の経路、`relabel` の値）が根拠と一致する。根拠は、その図を使う場面の行の `source` と、同じスライドのテキストのブロックの `source`。利用者の考えを図にしたもの（そのスライドの意図か章の意図が `by: user` で、図がその意図に書かれた内容をそのまま描いている）は対象外 | fact-checker | must |
| S-F4 | 出どころのない事実の記述がない。`source` がなく、事実を述べている行と、スライドのテキストのブロックを挙げる。利用者の意図（構成メモの `by: user` の `intent`）に書かれた内容を言い換えただけの行とブロックは見ない（利用者の考えには、突き合わせる相手がない）。利用者の章でも、台本が足した具体例・数値・固有の名前が事実を述べていれば挙げる。つなぎの文と、スライドの説明だけの行は挙げない | fact-checker | should |
| S-F5 | スライドのテキストに書かれた事実が、出どころから言える。`source` のあるブロック（段落・箇条・小見出し）の文が、その `source` から言える。定義や引用の囲み（`quote`）は、囲みの下に出る出どころを開いて、文が原文と合っているかを見る（訳したものなら意味が変わっていない。原文にない語を足していない、限定を落としていない）。見出しと言いたいこと（`statement`）が事実を述べているときは、同じスライドのブロックの `source` と、そのスライドを使う場面の行の `source` を根拠にして見る | fact-checker | must |
| S-D1 | 意図が処理の流れを追う場面で、流れているデータ（トークン・リクエスト・レコード等）が画面に出ていて、何が渡っているかが分かる（VG-1）。箱の関係を見せたいだけの場面と、流れのない図（表・比較・ベン図など）の場面は対象外 | director | should |
| S-D2 | **声と画面（VG-3・VG-6）**: 原稿がその行で説明しているものと、その行の動作が出す・強調するものが同じで、声と画面が同じ所を指している。説明と画面がずれている（声は B の話なのに A が光る）は must。1 行に別々の変化が重なって視線が割れ、どこを見ればよいか分からない（`sub_forced` も手がかり）は should。続けて起きる小さな動作や、対になる 2 つを同時に出すのは 1 つの変化に見えるので合格 | director | must（説明と画面がずれている）/ should（変化が多く、どこを見ればよいか分からない） |
| S-D4 | **ほかの見せ方（周りを薄くする VG-4・具体的な 1 件 VG-5・出る順と話す順 VG-9 など）**: その場面の見せ方が、意図に対して効いている。VG の「代償」が出ている（`focus` したまま話が移ってどこを見ているか分からない、出る順と話す順がずれて目と耳が別の所にある、場面ごとに別の点が出て 1 件の行方が追えない）のは FAIL。意図が 1 件の行方を追わせたいのに抽象のまま進む、のように効く所を逃しているのも FAIL。`evidence` には、照らした意図の文に加えて、どの VG の「聴衆に起こること」か「代償」に当たるかを書く | director | should |

S-F3 と S-D3 は欠番（`README.md` の「欠番と、書き直した ID」）。S-F4 の指摘には、`suggestion` に「調べて出どころを付ける」か「利用者の考えとして言う」かを書く。

S-W12・S-W13 の `evidence` には、比べたスライドの文言と字幕の文言を並べて引用し、意図に照らしたときは、照らした意図の場所と文も引用する。指摘の場所（`where`）は、行への指摘なら行の id、スライドのテキストへの指摘なら、そのスライドを最初に使う場面の id にして、`problem` の頭にスライドの id とブロックの id を書く（`../writing/review-format.md`）。

## 較正の例

- **事実の言い過ぎを should と付けた**（過去の台本レビュー）: 「書けなかったときの例外を 'already-exists' として返す」（実際は条件付き書き込みの失敗の例外だけ）、「API はトークンの無いリクエストを 401 で拒否する」（ヘルスチェックの経路は通る）。どちらも S-F1 の FAIL で must。should と付けたためループで止まらず、人が後から直した

- **主語・目的語・接続の言葉を省いた**（利用者の指摘「主語や目的語、接続詞など、重要な部分を省略して台本を書くことが多い」）: 「公開して、指して直す」（何を指すのか）、「コマを並べたページで確認します。問題なければ合成します。」（誰が、何を）。スライドの見出しや箇条は短い句なので、そのまま字幕にすると要素が落ちる。意味が取れなければ must、取れるが聞き手が補う必要があれば should → S-W7（SP-15）。比べる相手や一致の相手が落ちていれば S-W1（TW-2）
- **行どうしがつながらない**（利用者の指摘「前の文章との繋がりがなくぶつっと切れている印象を抱くことがとても多い」）: 初稿が、伝える内容の項目 1 つを 1〜2 行に置き換えて並べた形で、前の行を受ける言葉がなかった。スライドの箇条を 1 項目ずつ字幕に置き換えたときにも、同じことが起きる。1 行ずつは正しいので、S-W1・S-W7 では見つからない → S-W11
- **章扉が型になった**（利用者の指摘）: どの章も「この章では、〜を話します」で始まり、問いの後に答えまで言っていた → S-W11（SP-12）
- **用語をやさしい言葉に言い換えた**（利用者の指摘「過度に単純化した言い換えは誤解を招く」）: 評価役が「聴衆が知らない語」と指摘した規格の用語を、進行役が別の言葉に置き換えた。規格・原典の用語はそのまま使い、意味を説明する文を足す → S-W7（SP-16）。評価役の `suggestion` も「説明の文を足す」と書く
- **項目の説明に全体の性質を混ぜた**（利用者の指摘）: 4 つの活動を順に説明する行の中で、4 つ全体を繰り返すことまで言った。項目は「名前の文＋意味の文」で言い、繰り返すことは 4 つを言い終えた後の行で言う → S-W7（SP-17）
- **1 桁ずつ読ませて遅くなった**（利用者の指摘。s4 / l6）: 規格番号 ISO 9241-210 の誤読（「ヨンジュウ」）を直すために、`read` を「きゅう、に、よん、いち、の、にひゃくじゅう」と読点で区切った。読みは合ったが、間が 7 つ入って 1 行が 10 秒になった。中黒で区切れば 7.5 秒 → S-W9
- **内部の用語が字幕に出た**（過去の指摘「『地図』という言葉は比喩が過ぎる」）: 「地図だよ。」「1 つ目の目玉なのだ」。どちらも演出の文書の用語で、聴衆には意味が無い → S-M2
- **造語**（過去の指摘「不自然な言葉の使い方が目立つ」）: 「目印ハズセッション」「試行印」「読み書き役」「要なのだ」。hasSession は「ログイン済みかどうかを示す値」、試行印は「再試行を 1 回に限るための値」と仕組みの言葉で言う → S-W2
- **語尾が混ざった**（過去の指摘「ずんだもんの語尾が徹底しきれていない」）: 「〜取るよ。」「〜戻されるんだ。」「〜なのだ。」が混在 → S-M3
- **初めて見る人に分からない語から始めた**（過去の台本の冒頭）: 「題材を渡すと、何が起きて再生ページになるのでしょうか」。聴衆には「題材」「再生ページ」が何か分からない → S-W6
- **聴衆の関心のない規格の名前を読み上げた**（利用者の指摘「ISO 9241-210 をわざわざ説明に出す必要はない」）: 営業向けの UX の動画で、定義の行に規格の番号を読み上げていた。聴衆が知りたいのは定義の中身なので、番号は行の `source` とスライドの出どころの欄に置けば足りる。聴衆が規格を扱う職種なら、番号を言う意味がある → S-W5
- **名詞の前に説明を重ねた**（過去の台本）: 「進行役がチャットでページを公開する仕組み Artifact に載せ」。内部の呼び名「進行役」が説明なしに出て、長い説明の後ろに名前が来て聞き取れない → S-W5（SP-2）
- **スライドの文字を読み上げた**（判定の目安として置いた例。実際の通しで出たものではない）: スライドの箇条が「期待を持つ」「使いやすさを感じる」「また使いたいかが決まる」で、字幕が「利用者は期待を持ちます。」「使いやすさを感じます。」「また使いたいかが決まります。」と続いた。字幕は、3 つがどういう順に起きるのか、どれがユーザビリティに当たるのかを説明する → S-W13
