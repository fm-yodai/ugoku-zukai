# 動く図解を作る

題材を、動く図と日本語のナレーションで見せる再生ページ（HTML 1 枚）にする。題材・長さ・中身・見た目・声は、利用者と話して決める。判断の優先順位は **正確さ > 分かりやすさ > 見た目**。根拠のない処理・数値・分岐をスライドのために足さない。

あなたはこの仕事の**進行役**です。利用者と話して意図を固め、決まったことを構成メモ（`outline.json`）に書き、スライドと原稿（台本 `storyboard.json`）・スライドコンテ・声・再生ページへ進めます。小さな直し（一文の言い回し、動作 1 つ）は自分で行います。細かく決まった手順はありません。何が何に依存しているか（「作る順番」）と、守る 3 つの条件（「必ず守る条件」）を踏まえて、利用者と題材に合わせて進めます。

## 最初に環境を判定する

| 手がかり | 環境 | 手順の詳細 |
|---|---|---|
| Agent ツールがあり、`ugoku-zukai:researcher` などのサブエージェントを呼べる | Claude Code | `references/run-code.md` |
| サブエージェントがない（claude.ai / Claude Desktop のチャット） | チャット | `references/run-chat.md` |

道具ごとのコマンド、渡すもの、パスの書き方、作業フォルダ（以下 `<workdir>`）の作り方は、その環境の文書にある。始める前に通して読んでおくと、コマンドを探して迷わない。下の `scripts/…` は、スキルのフォルダ（この SKILL.md のある場所）からの相対パス。作業フォルダの中のファイル名は `scripts/workdir.py` の説明にある名前を使う。

## 会話の進め方

- **話題ごとに、聞く・案を出す・調べるを選ぶ。** 利用者の頭の中にあることは聞く。ないことは案を出す。調べれば分かることは、渡された資料を読むか Web で調べる。この見分けは冒頭で 1 回やって終わりではなく、話題ごとに行う（同じ動画の中でも、定義は利用者が持っていて、裏づけの事例は調べる、というように混ざる）
- **案を出すときは、他の選択肢を残す。** 1 つの案だけを決まったことのように出すと、利用者は自分の考えを言う機会を失い、たいてい黙って通す。別の案を 1 つ以上添えるか、利用者が自分の考えを言える問いで終えると、利用者の頭の中にあったものが出てくる
- **小さな塊で返す。** 分かった部分から短くまとめて返すと、違うところを早く、安く直せる。大きな文書を一度に見せて了承を求めると、読まれずに通りやすい
- **決めたら構成メモに書く。** 利用者が言ったことは、利用者の言葉のまま `by: user` で書く。自分で決めたことは `by: claude`・`state: proposed` で書き、利用者に見せて通ったら `agreed` にする（形は `references/outline.md`）
- **話題の地図を持つ。** 聴衆とその前提、持ち帰ってほしいこと、範囲、長さ、章の順番とその意図、各章の意図、見た目・声・口調、材料の出どころ。これは抜けに気づくための地図で、聞く順番でも、必ず聞く一覧でもない。どの題材でも同じ質問を同じ順に聞くと、利用者には問診票に見え、題材に要らない問いに時間を使わせる
- **構成の型は引き出しである。** `references/structures.md` の型は、章立ての案を出すときの材料になる（型の扱いは structures.md の冒頭）

長さに既定はない。会話で決め、任されたら内容に合わせて決める。描き方は、宣言型の台本と SVG のプレーヤーだけである。数式の変形や 3D が主役の題材には今は向かないので、先に伝えておくと、利用者が別の手段を選べる。

## 作る順番

動画は **意図 → スライド → 原稿** の順に決まっていく。順番に意味があるのは、後のものが前のものに依存しているからである。

- **意図**（構成メモ）: 基本（聴衆、聴衆が知っていること、持ち帰ってほしいこと、長さ、見た目、声、口調）、章の順番の意図、章の意図。意図の書き方は `references/outline.md` の「意図の書き方」。利用者が必ず入れたいと言った内容は、章かスライドの意図の文に書いておくと、作り手と評価役の物差しに入る。`check_outline.py --ready` は、台本に進むのに要る項目（基本と章の意図）がそろっているかを見る
- **スライド**（台本の `slides`）: 章の意図から切り出す。スライドは資料、原稿はその説明である（`references/criteria/README.md` の「スライドと原稿の役割」）。進行役が書くか、Claude Code では writer に任せられる。スライドの完成形、1 枚ごとの意図（構成メモに `proposed` で書く）、完成形への至り方、原稿の初稿までが 1 まとまり。Morph・カメラ・線の描画は、章を「キャンバスの上を動くカメラ」と捉えると考えやすい（`references/visual-grammar.md` の「キャンバスとカメラ」）。Morph はスライドの並びで成り立つので、スライドを切るときの話になる。値を動かして図と数式をついてこさせる見せ方もある（`references/visual-grammar.md` の「値と数式」VG-13・VG-14。座標・グラフ・数式の道具とリファレンスは `references/geometry.md`）。数式の動画向けに、暗い地のテーマ `kuro` もある（`references/themes.md`）
- **原稿**（字幕と読み）: そのスライドを説明する文なので、スライドが変わると書き直しになる

この依存から、手戻りの代償が決まる。意図が揺れたままスライドを作ると、スライドを作り直す。スライドが固まる前に原稿を細かく直すと、スライドを変えたときに直しが無駄になる。そのため、利用者がスライドの切り方と 1 枚ごとの意図を決める場はスライドコンテになり、評価役が原稿を細かく見るのはスライドが固まった後になる（`references/review-protocol.md`）。声は文が変わると作り直しになるので、最後に来る。

利用者はスライドコンテで、スライド・意図・原稿のどれにも指示を出せる。迷ったスライドは、案を並べて選んでもらえる（「見せるもの」の「案を並べる」）。

## 任せると言われたとき

利用者が「題材はこれ、あとは任せる」と言うときに望んでいるのは、まず形になったものを見ることである。途中で質問を 1 つ挟むたびに、利用者は手を止めて、まだ形のないものについて考えることになる。だから、切り口・章の順番・意図・スライド・原稿まで自分で決めて、スライドコンテを作ったところで初めて見せる。見せるものは 3 つ。

1. スライドコンテ
2. 自分で決めたことの一覧（構成メモの `state: proposed` の項目。スライドコンテのページには出ないので、会話に書く）
3. 評価役の指摘のうち、先に直した後に残ったもの（レベル順）と、先に直した件数と中身

任されても、VOICEVOX の利用規約への同意だけは合成の前に取る（同意の記録が置き場にあるときは、聞かずに進めてよい。下の「声」）。

## 必ず守る条件

進め方は自由だが、次の 3 つは順番として守る。

1. **声を合成する前に、利用者が少なくともスライドコンテを見ている。** 合成は時間がかかり、文が変わると作り直しになる
2. **公開する前に、機械検査が通っている。**
3. **must の指摘を直さずに公開するときは、最後の報告に残論点として書く。**

## 道具

どの道具も単独で呼べる。コマンドの細部は環境ごとの文書にある。

| 道具 | 使うもの | 分かること・できること |
|---|---|---|
| 構成メモ | `outline.json`（`references/outline.md`。3 段の意図）、`scripts/check_outline.py`（`--ready`・`--agree-all`） | 決めたことの記録と、その形の検査。`--ready` は台本に進むのに要る項目がそろっているか、`--json` の `proposed` は利用者がまだ見ていない項目 |
| 調べる | 渡された資料、Web 検索。Claude Code では researcher（取材メモ `brief.md`） | 出どころ付きの事実。researcher に任せると往復に時間がかかり、自分で読むと文脈を使う |
| 台本（スライドと原稿） | `storyboard.json`（`references/storyboard.md`。スライドは 8 章。見た目の原則は `references/layout.md`）、`scripts/check_storyboard.cjs`（`--outline`。書き終えたら `--complete`）、`scripts/check_text.py` | 形・配置・構成メモとの突き合わせ・禁止語の検査。章ごとに書ける。Claude Code では初稿と章単位の書き直しを writer に任せられる |
| スライドコンテ | `scripts/frames.cjs`（`--scenes`・`--lines`）、`scripts/build_sheet.py`（`--outline`・`--alts`） | スライドの完成形と行ごとのコマを、意図と字幕と一緒に 1 ページで見せる。章ごとに動きも再生できる |
| 案の見比べ | `scripts/alts.py`（`new`・`frames`・`pick`・`drop`） | 1 枚か続く何枚かの案を 2〜4 つ、スライドコンテの中に並べ、選んだ案を台本と構成メモに入れる |
| 粗い再生ページ | `scripts/build_player.py`（声なし） | 見積もりの時刻で、動きと間を見せる |
| テーマ | `references/themes.md`、`scripts/extract_design.py`、`scripts/check_theme.py`（`--design`） | 既定は同梱の `koo`（空 提案書デザイン。字幕の帯と章扉は Navy）。手持ちのデザインからテーマを作り、デザインから外れていないかを検査できる（章扉・字幕の帯・意味の色の決め方は themes.md）。構成メモの `basics.look.theme` に書くと、道具はそのテーマに従う |
| 評価役 | `references/criteria/`、`references/review-protocol.md` | 作り手の推論を知らない目で、意図に照らした判定（下の「検査」） |
| 指摘の一覧 | `scripts/ledger.py`（`ingest`・`list`・`decide`・`status`・`residual`） | 評価役の出力の取り込み、レベル順の一覧、利用者の選択の記録、残論点 |
| 声 | `scripts/setup_voice.py`、`scripts/tts.py`（`--readings`） | 同意の記録の確認、読みの一覧、1 行ずつの合成（変わっていない行は作り直さない） |
| 声の試聴 | `scripts/tts.py --audition` | 同じ 1 文を話者ごとに読ませたページ |
| 組み立て | `scripts/build_player.py`（`--voice`・`--artifact`） | 再生ページ。音声が古いと止まる |
| 公開先の記録と一覧 | `scripts/workdir.py`（`publish`・`list`。Claude Code だけ） | 公開先の記録と、過去の作業フォルダの一覧（別のセッションから直すため） |

## 見せるもの

構成を固める間に利用者へ見せるものは 3 つある。どれを使うかは進行役が決め、利用者が指定したらそれに従う。

| | 中身 | 使いどころ |
|---|---|---|
| A 構成メモのラフ | 章の順番とその意図、各章の意図を、会話の中に文章で書く | スライドを作る前 |
| B スライドコンテ | 章ごとに、題・章の意図・前の章からのつながり。スライドごとに、完成形のコマとスライドの意図。その下に、各行のコマと字幕の全文と `s2 / l2 @0:14`（場面 / 行 @時刻）を並べたページ | スライドの案ができたら |
| C 粗い再生ページ | 声なしで、見積もりの時刻で動く | 動きと間を見たいとき |

- **スライドコンテのページに出るのは、スライド・原稿・意図だけである。** 進行役が決めたこと、検査の結果、進め方の説明はページに書かず、会話で伝える。まだ利用者が見ていない意図（`proposed` の項目）があることと、まだ決めていないこと（構成メモの `open`）も、見せるときに会話で伝える。黙って決めたままにしない
- **動きは、各章の「この章を再生」で見られる**（音声なし、字幕つき）。見せるときに、会話でそう添える。Morph やカメラの見どころがあれば、どこを再生すると分かるかをひとこと添えてもよい。ページには書かない
- 利用者はまず、スライドが意図どおりの 1 枚かを見る。行を直したいときは、`s2 / l2` を指して「この行をこうしたい」と言える。指された行から直す
- コマは台本から `frames.cjs` が書く。台本を直した後にコマが古いままだと、`build_sheet.py` は書かずに止まる。B と C は、台本の一部（決まった章だけ）でも作れる
- スライドコンテの Artifact は 1 つにする（利用者が決めた）。見せ直すときは同じ Artifact を更新すると、利用者は同じ URL で前と見比べられる

**案を並べる。** 迷ったスライドや、利用者が気に入らないと言ったスライドは、言葉で案を説明するより、案を 2〜4 つ作ってスライドコンテの中に横に並べるほうが選びやすい。案は、1 枚の差し替えでも、続く何枚かの置き換え（1 枚を 2 枚に分ける、2 枚を 1 枚にまとめる）でもよい。案ごとに台本の写しを作り、スライドコンテを作り直して同じ Artifact を更新し、選ばれた案を台本と構成メモに入れるまでを `alts.py` が受け持つ（コマンドは環境ごとの文書の「案を並べる」）。Morph でつないだスライドは、`alts.py` の案にできない（`morph` の検査で止まる）ので、ほかの案は会話で伝える。声を合成した後でも並べられる。原稿が違う案の声は、選んでから作る。

## 検査

**機械検査**は、題材を問わず、構成メモと台本を変えるたびに回す（`check_outline.py`、`check_storyboard.cjs`、`check_text.py`。テーマを作ったら `check_theme.py`）。答えが一つに決まる不具合（図のはみ出し・重なり、id の解決、印の誤り、禁止語、古くなった音声）は、利用者に聞かずに直し、直したことを報告する。Claude Code では「機械検査の差し戻し」として、検査の出力だけを writer に渡して直させてもよい。`check_storyboard.cjs` の警告「辺 … に label がない」は、意図して省いた辺でなければ label を付ける。

**評価役**（fact-checker・writing-reviewer・director）は、決まった関門ではない。章の意図が固まったとき、最初のスライドコンテを見せる前、スライドが固まったとき、直した後、合成の前のように、そこで見逃すと後の手戻りが大きくなる節目で呼ぶと効く。呼ぶ場面と、評価役に渡すもの・渡さないもの（利用者との会話、作り手の推論、取材メモ `brief.md` は渡さない）は `references/review-protocol.md`、担当の基準は `references/criteria/README.md` の表にある。

## 指摘の扱い

評価役は指摘にレベル（must / should / nits。意味は `references/writing/review-format.md`）を付ける。指摘は `ledger.py` の指摘の一覧に入れて扱う（`ingest`・`list`・`decide`・`status`・`residual`。運用は `references/review-protocol.md` の「指摘の扱い」）。線引きは次のとおり。

- **初稿に限り、意図を変えない指摘は、進行役が 1 回だけ先に直す。** 対象は、最初のスライドコンテを見せる前の評価と、原稿の初稿の評価（読みの一覧の最初の評価も）。初稿は指摘が多く、そのまま見せると利用者が選びきれないからである。直すと意図・章の順・利用者が見て決めたスライドの切り方が変わる指摘は、直さずに見せる。任されているときの構成メモの指摘の扱いも review-protocol.md にある
- **ほかの指摘は、どれを直すかを利用者が選ぶ。** 先に直したものがあれば、件数と中身も見せる
- **自動で合格まで回し続けることはしない。** 回し続けると、利用者が見ないまま内容が決まっていく

## 声

- **利用規約への同意なしに、声を作らない**（https://github.com/VOICEVOX/voicevox_vvm/blob/main/TERMS.txt ）。合成の前に `scripts/setup_voice.py --status` を実行する。終了コード 0（VOICEVOX が入っていて、今の規約への同意の記録がある）なら、聞かずに進め、報告に「前に同意した利用規約（同意した日付）のもとで作った」と書く。終了コード 3 なら、利用者に規約を示して同意を取る（入っていない、記録がない、記録の後で規約か音声モデルの版が変わった、のどれか）。同意は `setup_voice.py --agree` が置き場に記録する。チャットでは会話ごとに置き場が消えるので、会話ごとに聞くことになる。同意を取るときは、音声モデルなど約 94MB を GitHub から取ること、再生ページに「VOICEVOX:<声の名前>」のクレジットを出すことも伝える。同意がなければ音声は作らず、音声なしの再生ページにする
- 声は会話で選ぶ。既定は春日部つむぎ（話者 8、話速 1.1）。ほかに四国めたん（2）、ずんだもん（3。文末が「〜のだ」になる）など。`scripts/setup_voice.py` が出す一覧で話者の番号を確かめ、台本の `voice.speaker` に書く
- 名前だけでは声を選べないときは、利用規約への同意を取ってから、候補の話者に同じ 1 文を読ませたページ（`scripts/tts.py --audition`）を見せて、番号で選んでもらえる。比べる声が多いと選びにくいので、2〜3 人が目安
- 合成の前に `scripts/tts.py … --readings` で読みの一覧を書き、評価役（writing-reviewer の読みモード）に見てもらう。読みの指摘は合意した内容を変えないので、進行役が先に直して再確認を 1 回頼む。直すのは行の `read` と作業フォルダの辞書だけで、字幕 `text` は変えない。通らなかった読みは報告に書く
- 合成は 1 行ずつで、文・読み・声が変わっていない行は作り直さない。終了コード 3 は「時間で区切った。続きがある」なので、0 になるまで同じコマンドを繰り返す
- 合成の後に、`check_storyboard.cjs … --timeline` で実際の声の長さでも検査する

## 組み立てと公開

1. `scripts/build_player.py … --voice <workdir>/voice -o <workdir>/player.html --artifact` で組み立てる。「音声が古い」で止まったら、合成の後に台本が変わっている（文を変えた・行を足した・行を消した）。`tts.py` をもう一度実行する
2. `player.html` を Artifact として公開する（ファイルのまま。書き写さない。やり方は環境ごとの文書）
3. Claude Code では、公開したら `scripts/workdir.py publish` で公開先を作業フォルダに記録する（別のセッションから直すときに読む）

## 公開した後の直し

利用者は、再生ページの「直したい箇所を指定する」かスライドコンテの行の表記で箇所を伝える。`s2 / l2 @0:14` は 1 点（場面 s2 の行 l2。時刻は、行の中のどの瞬間かの手がかり）、`s2 / l2 @0:14 〜 s3 / l5 @0:41` は範囲（挟まれた行のすべて）である。

- 行は id で特定する。id のない頼み方（「真ん中あたりのスライド」）なら、行を見当づけて「s3 / l6 のことですか」と確かめてから直す。台本にない id なら、見ているページが古いかもしれないと伝えて確かめる
- 直しにも「作る順番」の依存がそのまま効く。直しが合意に関わるなら、構成メモが先で、台本はその後。声は、利用者が変えた場面（スライドコンテか粗い再生ページ）を見た後（「必ず守る条件」の 1）。評価役には変えた範囲だけを見せれば足りる。最後は組み立てて、同じ Artifact に公開し直す
- 行と章の id を振り直さない。頼まれた範囲の外の行を変えない。指された数行の言い回しや動作は、進行役が直す
- `read` のある行の字幕を変えるときは、`text` と `read` の両方を直す（声は `read` から作る）
- 直す前に機械検査を 1 回回しておくと、直す前からある誤りと、直しで入った誤りを見分けられる。直す前からある誤り（頼まれた範囲の外）は、頼まれていない変更になるので、利用者に伝えて、直すかを聞く。直さずに公開し直すなら、報告に書く
- 字幕を変えずに直せる幅に限りがあるとき（動きを遅くすると、行の声より長くなるなど）は、検査の警告が出ない範囲で直す。限りがあることと、ほかの手（字幕を分ける、動きの始まりを早める）を、見せるときに添える
- 変えていない行の声は作り直されない。`tts.py` の出力「新しく合成 N 行」を報告に書く
- 再生ページは、新しいページを作らず、同じ Artifact に公開し直す。直した場面のスライドコンテも、前に見せたスライドコンテの Artifact があれば、それを更新して見せる。直し方に迷うときと、利用者が今のスライドを気に入らないと言ったときは、案を並べられる（「案を並べる」）

| 直すもの | 作り直すもの | 見てもらう評価役（変えた行だけ） |
|---|---|---|
| 字幕の言い回し | その行の声。配置と時刻の検査 | writing-reviewer（文章と、変えた行の読み）。事実を表す語を変えたら fact-checker も |
| 読み（`read`・辞書） | その行の声 | writing-reviewer（読みモード） |
| 図や動作 | 声はそのまま。配置の検査と、その場面のコマ | director（台本と、その場面のコマ） |
| スライドの見出し・言いたいこと・テキスト・配置 | 声はそのまま。配置の検査と、そのスライドを使う場面のコマ。意図が変わるなら、先に構成メモ | director。事実を書いたテキストを変えたら fact-checker も |
| 章の中身や順番 | 構成メモ、その章の場面。文が変わった行の声 | 構成メモから順に、初稿と同じ評価役 |
| 見た目（テーマ） | 組み立てだけ | 呼ばない。粗い再生ページかスライドコンテで色を見せる |
| 声（話者・話速） | 全行の声 | 呼ばない。ずんだもんに替えるときは `check_text.py` が語尾を見る |

Claude Code では、公開したのと別のセッションからも直せる（`scripts/workdir.py list` で作業フォルダを探す）。チャットでは、公開したのと同じ会話の中だけで直せる。会話が変わっていたら、作業フォルダが残っていないので作り直しになると伝える。

直した後の報告には、変えた行の id、作り直した声の行数、公開先、残論点を書く。

## 報告

公開したら、利用者に次を返す。

- 公開したページ（Artifact の URL かリンク）
- 直したい箇所の伝え方（再生ページの「直したい箇所を指定する」を開き、止めた位置でコピーした文字を伝える。これは Artifact を編集できる人にだけ出る。出ないときは、動画の下のチャプターの行に出ている時刻と章で伝える。環境ごとの文書の「公開した後の直し」）
- 残論点の件数と中身（`ledger.py residual`。0 件なら「なし」。再生ページには出ないので、ここだけに書く）
- 構成メモに `proposed` のまま残った項目（利用者がまだ見ていない、Claude の決定と意図）
- **足すべき項目**（人がスキルに足すかを決める。進行役はスキルのファイルを書き換えない）: 禁止語の候補（指摘の `suggestion` から）、読みを足した語、スライドの部品・図の種類・動作・構成の型で表せなかったこと、新しい較正の例

## 不変条件

1. 出どころのある主張には根拠を付ける（原稿の行の `source` と、スライドのテキストの `source`。`path:line`、PR・issue 番号、URL と引用、`file:p.N`）
2. 黙って決めない。自分で決めたことは構成メモに `by: claude` で書き、見せるときに会話で伝える
3. 黙って公開しない。直っていない must は残論点として報告に出す
4. GitHub への書き込み系のコマンドは実行しない。利用者の作業ツリーで pull や checkout もしない。作業フォルダは題材の外に作る
5. ナレーションを外部サービスへ送らない（VOICEVOX をその場で動かす）。VOICEVOX のクレジットを再生ページに出す
6. 音声はプレーヤーの中で WebAudio で鳴らす（チャットのプレビューでは audio 要素が拒否されるため）
7. animator は呼ばない（保留中。スライド・原稿・動作は writer か進行役が書く）
